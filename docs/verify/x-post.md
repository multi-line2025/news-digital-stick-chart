# X に投稿した鎖の先頭のハッシュを、公開されたリポジトリの記録と照らす手順（T-029）

この文書は、オーナーの X の専用アカウントに投稿した「封印の記録の鎖の先頭のハッシュ」を、第三者が公開されたリポジトリの記録と照らすための手順である。投稿文は `src/sealer/post_text.py` が作る。投稿はオーナーが自分で行う。

`<!-- test:x-post -->` の印が付いたコマンドの塊は、`tests/sealer/test_post_text.py` が、このリポジトリの手元の複製の中で、そのまま実行する。壊した複製（記録の書き換え・末尾の切り詰め・投稿と違う値）では、同じ塊が失敗することも確かめている。

データ出典：GDELT Project（https://www.gdeltproject.org/）。本プロジェクトは GDELT Project と提携・承認の関係にありません。

## 1. 投稿文の形

```
seq N: sha256(sealed/ledger.jsonl lines 1-N)
<64 桁の16進>
<recorded_at> / BTC <高さ または pending>
<GDELT の引用の固定文（日本語か英語）>
```

- **N**：投稿を作った時点の、記録（`sealed/ledger.jsonl`）の最後の seq。
- **64 桁の16進**：記録のファイルの先頭 N 行（各行の末尾の改行を含む）のバイト列の sha256。投稿を作った時点では、記録のファイル全体の sha256 と同じである。seq N の時刻証明 `sealed/ledger.jsonl.seq00000N.ots` の対象（`ots info` の `File sha256 hash`）とも同じ値である。
  - 各行の `prev_hash` の鎖は、最後の行を含まない。この値は最後の行まで含むので、記録が公開されたあとで先頭 N 行のどれか（最後の行を含む）を書き換えたり、N 行より短く切り詰めたりすれば、値が合わなくなる。
- **recorded_at**：seq N の記録の `recorded_at`。記録した機械の時計による申告で、証明ではない。
- **BTC**：seq N 自身の `.ots`（`.bitcoin.ots` を含む）の Bitcoin の証明のうち、ヘッダの時刻が最も早いブロックの高さ。投稿を作った時点で確定していなければ `pending`。
- 記録の `kind`・`note`・`targets` は投稿に入れない。CLAUDE.md は、判定期間の前に投稿してよいのは封印の証明（ハッシュと時刻）だけと決めている。ハッシュから記録の中身は分からない（記録には、注記の文と、公開していないファイルの sha256 が入っており、推測して当てられる形ではない）。

### 投稿文を作る（運営側）

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -B src/sealer/post_text.py
```

標準出力が投稿文、標準エラーが文字数の数え方の内訳である。次のどれかに当たれば、投稿文を出さずに終了コード 1 で止まる。

- 記録の検証（`verify.py` と同じ。鎖・各 seq の `.ots`・ヘッダの照合）に通らない。
- `sealed/` にコミットしていない変更がある。投稿したハッシュを、公開されたリポジトリと照らせなくなるため。
- 文が決まった形に合わない。最後の行が、GDELT の引用の固定文と一字一句同じでない。URL が引用の 1 つ以外にある。
- 許可していないメールアドレスの形がある（`src/collector/privacy_scan.py` の `find_in_bytes` で調べる。push の前の検査と同じ規則）。
- プロジェクトの外の情報の形がある：絶対パス、`~/`、バックスラッシュ、UUID（VolumeUUID など）、IPv4 アドレス、この機械のユーザー名・ホーム・ホスト名・プロジェクトの絶対パス。
- 文字数が X の上限（280）を超える。

### 文字数の数え方

X（twitter-text の v3 の規則）に合わせ、安全側に上乗せして数える。ここで 280 以下なら、X でも 280 以下である。

- NFC に正規化してから数える。
- `http://` か `https://` で始まる URL は、長さによらず 23。
- U+0000〜U+10FF、U+2000〜U+200D、U+2010〜U+201F、U+2032〜U+2037 の文字は 1。それ以外（日本語の文字、全角の括弧や句読点など）は 2。改行は 1。
- 安全側の上乗せ：`ledger.jsonl` のような「ラベル.ラベル」の形は、X がリンクにすると 23 と数えるかもしれない。X が使うトップレベルドメインの一覧は、ネットワークを使わずに確かめられない。そのため max(実際の長さ, 23) と数える。
- 絵文字は符号位置ごとに 2（X は並び全体で 2）。投稿文には絵文字を使わない。

### 引用の選び方

英語と日本語の固定文のそれぞれで全文を作る。上限に収まるものだけを候補にし、重みの小さい方を選ぶ。重みが同じなら日本語を選ぶ。

- どちらの固定文を使っても、決定事項を満たす。
- 余裕の大きい方を選べば、seq や高さの桁が増えても止まりにくい。
- 数だけで決まるので、人が選ぶ余地がない。

いまの本文では、日本語の固定文の方が 3 小さい（日本語の固定文の全体が 117、英語が 120）。そのため日本語が選ばれる。

## 2. 照らせるのは、リポジトリが公開されてから

- リポジトリが公開される前は、第三者は投稿のハッシュを何とも照らせない。公開前に分かるのは、その日時にその値が投稿されたことだけである。
- 公開されたあとは、投稿より後のどの版の記録でも、先頭 N 行の sha256 が投稿の値と同じでなければならない。記録は追記のみなので、行が増えても先頭 N 行は変わらない。

## 3. 照らす手順（第三者）

リポジトリを手元に複製し、ルートで実行する。必要なものは git、python3、`shasum`（Linux では `sha256sum` でもよい）。

まず、投稿の値を変数に入れる。次は seq 4 の投稿の場合の例である。

```sh
SEQ=4                       # 投稿の 1 行目の N
POSTED=<投稿の 2 行目の 64 桁>
RECORDED=<投稿の 3 行目の / の前>
BTC=<投稿の 3 行目の BTC の後ろ（高さ または pending）>
export SEQ POSTED RECORDED BTC
```

続けて、次を実行する。どれかが合わなければ、そこで終了コード 0 以外で止まる。

<!-- test:x-post -->
```sh
: "${SEQ:?}" "${POSTED:?}" "${RECORDED:?}" "${BTC:?}"
# (1) 記録が SEQ 行以上あること（末尾の切り詰めが無い）
test "$(( $(wc -l < sealed/ledger.jsonl) ))" -ge "$SEQ"
# (2) 記録の先頭 SEQ 行の sha256 が、投稿の値と同じであること
GOT=$(head -n "$SEQ" sealed/ledger.jsonl | shasum -a 256 | cut -d' ' -f1)
echo "記録の先頭 $SEQ 行の sha256: $GOT"
test "$GOT" = "$POSTED"
# (3) SEQ 行目が seq SEQ の記録で、その recorded_at が投稿と同じであること
sed -n "${SEQ}p" sealed/ledger.jsonl | grep -F "\"recorded_at\":\"$RECORDED\",\"seq\":$SEQ," > /dev/null
# (4) 鎖・対象・時刻証明・ヘッダの検証が通り、seq SEQ の .ots の対象が投稿の値であること
PYTHONDONTWRITEBYTECODE=1 python3 -B src/sealer/verify.py all --rev auto > verify-out.txt
grep -F "対象 = 記録の先頭 $SEQ 行の sha256 $POSTED  一致" verify-out.txt
# (5) 投稿に高さがあれば、seq SEQ の .ots にその高さの証明があり、ヘッダと照合できること
if [ "$BTC" != pending ]; then grep -F "seq $SEQ: 高さ $BTC のヘッダと照合した" verify-out.txt; fi
echo "投稿と記録は一致する"
```

`verify-out.txt` は手元に作る出力のファイルで、記録の一部ではない（照らし終わったら消してよい）。

- (2) が合わないとき：投稿のあとで、先頭 N 行のどれかが書き換えられたか、記録が差し替えられた。
- (1) が合わないとき：投稿のあとで、記録の末尾が切り詰められた。
- (4) の `verify.py` を信用しない場合は、`docs/verify/periods-seal.md` の 4章・5章の標準の道具（`head`・`shasum`・`ots info`・`ots verify`）で同じことを確かめられる。seq N の `.ots` の `File sha256 hash` が投稿の値と同じであることを見る。
  ```sh
  .venv/bin/ots info "$(printf 'sealed/ledger.jsonl.seq%06d.ots' "$SEQ")" | grep 'File sha256 hash'
  ```
- (5) で照合するのは、ヘッダのマークルルートと作業量だけである。そのヘッダが Bitcoin の本当の鎖の、その高さのブロックかは、`docs/verify/periods-seal.md` の 5章の方法で別に確かめる。

## 4. 何が示せて、何が示せないか

示せること

- 投稿の時刻（X が表示する時刻）より前に、記録の先頭 N 行がその内容で存在したこと。投稿の時刻は X による表示で、OpenTimestamps の証明とは別の、運営の外の時刻の証人になる。
- 投稿のあとに公開された記録が、先頭 N 行を書き換えていないこと、切り詰めていないこと。

示せないこと

- 投稿より前に、別の記録の系列を作って捨てたことが無いこと。投稿が示すのは、投稿の時点の記録だけである。
- 投稿が後で消されたり、別の値が投稿されたりしていないこと。X の投稿はアカウントの持ち主が消せる。照らす人は、投稿の第三者のアーカイブ（Internet Archive など）も合わせて見るとよい（下の 5章の提案）。
- 記録の中身（`kind`・`note`・`targets`）の正しさ。それは `docs/verify/periods-seal.md` の手順で確かめる。

## 5. 投稿する時機の案

案であり、決めるのはオーナーである。

1. 今の鎖の先頭（seq 4。2026-10-08 時点）を、最初に投稿する。
2. そのあと、新しい封印の記録を追記するたびに、投稿する。手順は次のとおり。
   1. 記録を追記する。
   2. stamp で `.ots` を作る。
   3. コミットする。
   4. `post_text.py` で投稿文を作り、投稿する。
   - Bitcoin での確定は待たない（`pending` のまま投稿してよい）。投稿そのものが、運営の外の時刻の証人になるため。確定はあとで `.bitcoin.ots` として記録に残る。
3. 特に、関門の記録（`threshold-access`、`method-access`、今後の前向きの予言の週ごとの封印）は、追記してすぐに投稿する。関門の前の鎖を固定しておけば、関門のあとで前の記録を差し替えたことが分かるため。
4. 投稿ごとに、その投稿を第三者のアーカイブにも保存することを提案する。投稿が消されても照らせるようにするため。保存先と手順は、この文書の範囲の外なので、別のタスクとしてリードに提案する。
5. 投稿の前に、`post_text.py` の止まる条件（1章）に当たらないことを確かめる。手で文を直さない。直したくなったら、`post_text.py` を直すタスクにする。
