# X に投稿した鎖の先頭のハッシュを、公開されたリポジトリの記録と照らす手順（T-029）

この文書は、オーナーの X の専用アカウントに投稿した「封印の記録の鎖の先頭のハッシュ」を、第三者が公開されたリポジトリの記録と照らすための手順である。投稿文は `src/sealer/post_text.py` が作る。投稿はオーナーが自分で行う。

**投稿は、オーナーの明示の承認のあとに限る**（T-029 差し戻し1回目の M-1）。承認は、オーナー本人の発言として `reviews/` に原文で記録する。

- 封印のハッシュの投稿は、2026-10-08 にオーナーが承認した（`reviews/T-029.md` の最後の節。CLAUDE.md の「公開前の検査」）。
- 試運転の手順2の「公開はしない」と、記録の seq 1・2 の注記「封印したことは公開しない」は、記録の中身を指す。ハッシュの投稿はこれに当たらない（同じ決定）。
- 投稿の決まり：封印の記録を書き足すたびに、すべての記録を、その記録の時刻（recorded_at）から24時間以内に投稿する（同じ決定）。照らし方は5章。
- `post_text.py` は投稿文を作るだけで、承認の有無は確かめない。

## 1. 投稿文の形

```
sha256(sealed/ledger.jsonl seq 1-N)
<64 桁の16進>
<recorded_at> / BTC <高さ または pending>
<GDELT の引用の固定文（日本語か英語）>
```

- **N**：投稿を作った時点の、記録（`sealed/ledger.jsonl`）の最後の seq。`--seq N` を付ければ、その seq。記録の N 行目が seq N の記録である（鎖の規則。`docs/verify/periods-seal.md` の 1章）。
- **64 桁の16進**：記録のファイルの先頭 N 行（seq 1〜N の行。各行の末尾の改行を含む）のバイト列の sha256。
  - 投稿を作った時点では、記録のファイル全体の sha256 と同じである。
  - seq N の時刻証明 `sealed/ledger.jsonl.seq00000N.ots` の対象（`ots info` の `File sha256 hash`）とも同じ値である。
  - 各行の `prev_hash` の鎖は、最後の行を含まない。この値は最後の行まで含む。そのため、記録が公開されたあとで先頭 N 行のどれか（最後の行を含む）を書き換えたり、N 行より短く切り詰めたりすれば、値が合わなくなる。
- **recorded_at**：seq N の記録の `recorded_at`。記録した機械の時計による申告で、証明ではない。
- **BTC**：seq N 自身の `.ots`（`.bitcoin.ots` を含む）の Bitcoin の証明のうち、ヘッダの時刻が最も早いブロックの高さ。投稿を作った時点で確定していなければ `pending`。
- 記録の `kind`・`note`・`targets` は投稿に入れない。CLAUDE.md は、判定期間の前に投稿してよいのは封印の証明（ハッシュと時刻）だけと決めている。ハッシュから記録の中身は分からない。記録には注記の文と、公開していないファイルの sha256 が入っており、推測して当てられる形ではないためである。投稿から分かるのは、封印の記録の件数、seq N の記録の時刻（申告）、ブロックの高さである。

### 投稿文を作る（運営側。オーナーの承認のあと）

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -B src/sealer/post_text.py
```

標準出力が投稿文、標準エラーが文字数の数え方の内訳である。次のどれかに当たれば、投稿文を出さずに終了コード 1 で止まる。

- 記録の検証（`verify.py` と同じ。鎖・各 seq の `.ots`・ヘッダの照合）に通らない。
- `sealed/` にコミットしていない変更がある。投稿したハッシュを、公開されたリポジトリと照らせなくなるため。
- 文が決まった形に合わない。
- 最後の行が、GDELT の引用の固定文と一字一句同じでない。
- URL が引用の 1 つのほかにある。
- 許可していないメールアドレスの形がある。`src/collector/privacy_scan.py` の `find_in_bytes` で調べる（push の前の検査と同じ規則）。
- プロジェクトの外の情報の形がある。対象は、絶対パス、`~/`、バックスラッシュ、UUID（VolumeUUID など）、IPv4 アドレス、この機械のユーザー名・ホーム・ホスト名・プロジェクトの絶対パス。
- 文字数が X の上限（280）を超える。

### 文字数の数え方

X（twitter-text の v3 の規則）に合わせ、少なく数えない側に上乗せして数える。ここで 280 以下なら、X が URL をリンクにするかどうかによらず、X でも 280 以下である。

- NFC に正規化してから数える。
- U+0000〜U+10FF、U+2000〜U+200D、U+2010〜U+201F、U+2032〜U+2037 の文字は 1。それ以外（日本語の文字、全角の括弧や句読点など）は 2。改行は 1。
- `http://` か `https://` で始まる URL は、max(実際の長さ, 23) と数える。X がリンクにすれば 23、しなければ実際の長さになるので、どちらの場合も少なく数えない（T-029 差し戻し1回目の L-2）。GDELT の URL は 29 文字なので 29 と数える。
- `ledger.jsonl` のような「ラベル.ラベル」の形も、max(実際の長さ, 23) と数える。X がリンクにすると 23 と数えるかもしれないが、X が使うトップレベルドメインの一覧は、ネットワークを使わずに確かめられないため。
- 絵文字は符号位置ごとに 2（X は並び全体で 2）。投稿文には絵文字を使わない。

### 引用の選び方

英語と日本語の固定文のそれぞれで全文を作る。上限に収まるものだけを候補にし、重みの小さい方を選ぶ。重みが同じなら日本語を選ぶ。

- どちらの固定文を使っても、決定事項を満たす。
- 余裕の大きい方を選べば、seq や高さの桁が増えても止まりにくい。
- 数だけで決まるので、人が選ぶ余地がない。

固定文だけの重みは、日本語が 123、英語が 126 である。日本語の方が 3 小さいので、いまの本文では日本語が選ばれる。

## 2. 照らせるのは、リポジトリが公開されてから

- リポジトリが公開される前は、第三者は投稿のハッシュを何とも照らせない。公開前に分かるのは、その日時にその値が投稿されたことだけである。
- 公開されたあとは、投稿より後のどの版の記録でも、先頭 N 行の sha256 が投稿の値と同じでなければならない。記録は追記のみなので、行が増えても先頭 N 行は変わらない。

## 3. 投稿 1 件を照らす手順（第三者）

リポジトリを手元に複製し、ルートで実行する。必要なものは git、python3、`shasum`（無ければ `sha256sum`）である。

### 3.1 投稿の値を変数に入れる

次は seq 4 の投稿の場合の例である。

```sh
SEQ=4                       # 投稿の 1 行目の「seq 1-N」の N
POSTED=<投稿の 2 行目の 64 桁>
RECORDED=<投稿の 3 行目の / の前>
BTC=<投稿の 3 行目の BTC の後ろ（高さ または pending）>
export SEQ POSTED RECORDED BTC
```

### 3.2 照合の塊をファイルに保存して実行する

次の塊を、リポジトリの外のファイル（例：`x-post-check.sh`）に保存し、リポジトリのルートで `bash x-post-check.sh` か `zsh x-post-check.sh` として実行する。

- `-e` は要らない。各検査は、合わなければ「合わない: (番号) 理由」を出し、その場で終了コード 1 で止まる。
- 端末に貼り付けて実行しない。止まるときの `exit` で端末が閉じるため。
- 全部が合ったときだけ、最後に「投稿と記録は一致する」と出て、終了コード 0 で終わる。
- ファイルは何も書かない（以前の版は `verify-out.txt` をリポジトリのルートに書いていた。T-029 差し戻し1回目の L-5 で、出力を変数に入れる形に改めた）。

<!-- test:x-post -->
```sh
# x-post-check.sh：投稿 1 件を記録と照らす。bash でも zsh でも、-e なしで動く。
fail() { echo "合わない: $*"; exit 1; }
sum256() { if command -v shasum >/dev/null 2>&1; then shasum -a 256; else sha256sum; fi; }
# (0) 投稿の値の形
[ -n "${SEQ:-}" ] && [ -n "${POSTED:-}" ] && [ -n "${RECORDED:-}" ] && [ -n "${BTC:-}" ] \
  || fail "(0) SEQ・POSTED・RECORDED・BTC のどれかが空"
case "${SEQ}" in ''|0*|*[!0-9]*) fail "(0) SEQ が正の整数でない" ;; esac
case "${POSTED}" in *[!0-9a-f]*) fail "(0) POSTED が小文字の16進でない" ;; esac
[ "${#POSTED}" -eq 64 ] || fail "(0) POSTED が 64 桁でない"
case "${BTC}" in pending) ;; ''|0*|*[!0-9]*) fail "(0) BTC が高さでも pending でもない" ;; esac
[ -f sealed/ledger.jsonl ] || fail "(0) sealed/ledger.jsonl が無い（リポジトリのルートで実行する）"
# (1) 記録が SEQ 行以上あること（末尾の切り詰めが無い）
LINES=$(wc -l < sealed/ledger.jsonl) || fail "(1) sealed/ledger.jsonl を読めない"
LINES=$((LINES + 0))
[ "${LINES}" -ge "${SEQ}" ] || fail "(1) 記録は ${LINES} 行で、投稿の seq ${SEQ} より短い（末尾が切り詰められた）"
# (2) 記録の先頭 SEQ 行の sha256 が、投稿の値と同じであること
GOT=$(head -n "${SEQ}" sealed/ledger.jsonl | sum256 | cut -d' ' -f1)
echo "(2) 記録の先頭 ${SEQ} 行の sha256: ${GOT}"
[ "${GOT}" = "${POSTED}" ] || fail "(2) 記録の先頭 ${SEQ} 行の sha256 が投稿の値 ${POSTED} と違う（書き換えか差し替え）"
# (3) SEQ 行目が seq SEQ の記録で、その recorded_at が投稿と同じであること
LINE=$(sed -n "${SEQ}p" sealed/ledger.jsonl)
case "${LINE}" in
  *"\"recorded_at\":\"${RECORDED}\",\"seq\":${SEQ},"*) echo "(3) ${SEQ} 行目は seq ${SEQ}、recorded_at ${RECORDED}" ;;
  *) fail "(3) ${SEQ} 行目が seq ${SEQ} の記録でないか、recorded_at が投稿の ${RECORDED} と違う" ;;
esac
# (4) 鎖・対象・時刻証明・ヘッダの検証が通り、seq SEQ の .ots の対象が投稿の値であること
VOUT=$(PYTHONDONTWRITEBYTECODE=1 python3 -B src/sealer/verify.py all --rev auto 2>&1) \
  || fail "(4) verify.py の検証が失敗した: $(printf '%s\n' "${VOUT}" | tail -n 3)"
case "${VOUT}" in
  *"対象 = 記録の先頭 ${SEQ} 行の sha256 ${POSTED}  一致"*) echo "(4) seq ${SEQ} の .ots の対象は投稿の値と同じ" ;;
  *) fail "(4) seq ${SEQ} の .ots の対象が投稿の値と違う" ;;
esac
# (5) 投稿に高さがあれば、seq SEQ の .ots にその高さの証明があり、ヘッダと照合できること
if [ "${BTC}" != pending ]; then
  case "${VOUT}" in
    *"seq ${SEQ}: 高さ ${BTC} のヘッダと照合した"*) echo "(5) seq ${SEQ} は高さ ${BTC} のヘッダと照合した" ;;
    *) fail "(5) seq ${SEQ} の .ots に、高さ ${BTC} の証明が無いか、ヘッダと照合できない" ;;
  esac
fi
echo "投稿と記録は一致する"
```

- (1) が合わないとき：投稿のあとで、記録の末尾が切り詰められた。
- (2) が合わないとき：投稿のあとで、先頭 N 行のどれかが書き換えられたか、記録が差し替えられた。
- (4) で `verify.py` を信用しない場合は、`docs/verify/periods-seal.md` の 4章・5章の標準の道具（`head`・`shasum`・`ots info`・`ots verify`）で同じことを確かめられる。seq N の `.ots` の `File sha256 hash` が、投稿の値と同じであることを見る。
  ```sh
  .venv/bin/ots info "$(printf 'sealed/ledger.jsonl.seq%06d.ots' "${SEQ}")" | grep 'File sha256 hash'
  ```
- (5) で照合するのは、ヘッダのマークルルートと作業量だけである。そのヘッダが Bitcoin の本当の鎖の、その高さのブロックかは、`docs/verify/periods-seal.md` の 5章の方法で別に確かめる。

### 4.3 投稿の ID から時刻を計算する（ネットワークを使わない）

```sh
ID=2107899885177704739
echo $(( (ID >> 22) + 1288834974657 ))        # 1791397470169（1970-01-01 からのミリ秒）
date -u -r 1791397470 +%Y-%m-%dT%H:%M:%SZ     # macOS。Linux では date -u -d @1791397470 +%Y-%m-%dT%H:%M:%SZ
python3 -c 'import datetime as d; ms=(2107899885177704739>>22)+1288834974657; print(d.datetime.fromtimestamp(ms/1000, d.timezone.utc).isoformat(timespec="milliseconds"))'
```

## 5. 投稿の有無と遅れを照らす手順（第三者。T-029 差し戻し1回目の M-2、T-034）

3章は投稿 1 件を照らす。それだけでは、運営が投稿する時機を選んだことを見つけられない。たとえば、`threshold-access` を追記してから、都合のよい系列だけを遅れて投稿する、ということができる。この章では、アカウントの投稿をすべて並べ、seq ごとの投稿の有無と、投稿の遅れを、投稿の決まりと照らす。

### 投稿の決まりと、決まりの前の記録（seq 1・2）の例外

投稿の決まり（2026-10-08 オーナー決定）：封印の記録を書き足すたびに、すべての記録を、その記録の recorded_at から24時間以内に投稿する。

- 投稿された時刻：seq k が投稿された時刻は、seq k 以上の投稿（ハッシュの合うもの）のうち、最も早い時刻とする。先頭 m 行のハッシュは、k ≤ m のすべての行を固定するため。
- 例外：決まりを決めた時点（コミット 80f7edd、2026-10-07T17:57:02Z）で、recorded_at から24時間を過ぎていたのは次の2件だけである。この2件は、遅れの判定から外す（遅れは表示だけする）。投稿に含まれていることは求める。
  - seq 1（2026-10-05T21:41:03Z）
  - seq 2（2026-10-06T09:58:57Z）
- seq 3（2026-10-07T13:45:11Z）と seq 4（13:45:22Z）は、その時点で約4時間しかたっていなかった。そのため、決まりの対象である。最初の投稿（4.2。2026-10-07T18:24:30.169Z）は、どちらにも約4.66時間の遅れで、決まりの中である。
- T-029 では例外を seq 1〜4 としていた。これは、リードが「seq 1〜4 は既に24時間を過ぎている」と伝えた事実の誤りによるもので、T-034 で seq 1・2 に正した（T-029 の監査 M-a）。
- 例外の範囲（seq 2 まで）は、`post_text.py` の定数 `PRE_RULE_LAST_SEQ` に固定してある。記録の件数や投稿の結果からは変わらない。照らす人が引数で変えることもできない。
- まだ投稿が無く、recorded_at から24時間たっていない seq は、「保留」と出す（合わないとはしない。T-029 の監査 L-c）。24時間を過ぎても投稿が無ければ、合わないとする。「今」は、照らす人の機械の時計である。

```sh
# x-post-list.sh：投稿の一覧を、投稿の決まり（すべての記録を24時間以内。seq 1・2 は例外）と照らす。

```

`check-posts` は、一覧のすべての投稿について次を確かめる。

- URL で書いた投稿のアカウントが @Dstickchart であること（大文字小文字は区別しない）。
- seq が記録の件数以下で、投稿のハッシュが記録の先頭 seq 行の sha256 と同じこと。
- 投稿の時刻が、その seq の recorded_at より後であること。

続けて、seq ごとに次を確かめる。

- 投稿された時刻（上の定義）と、遅れ（投稿 − recorded_at、投稿 − Bitcoin の確定時刻）を表示する。
- seq 3 以降は、遅れが24時間以下であること。
- 投稿が無い seq は、24時間たっていなければ保留、過ぎていれば合わない。seq 1・2 は、投稿が無ければ合わない。

記録全体についても、次を確かめる。

- どの seq も、recorded_at が、その seq の `.ots` の最も早い確定時刻（ヘッダの時刻）+ 3 時間より後でないこと（T-029 の監査 L-b）。
  - 記録は stamp の前に書くので、recorded_at は確定時刻より前のはずである。
  - 3 時間の余裕を取る理由：ヘッダの時刻は、実際に掘られた時刻より 1 時間ほど前にも、2 時間先にもなりうるため。
  - `post_text.py` で投稿文を作るときも、同じ検査で止まる。

値の扱い：

- `--max-delay-hours` の既定は 24（決まりの値）である。有限で 0 以上の数だけを受け付け、nan・inf・負の数は止める（T-029 の監査 L-a）。
- 既定と違う値を渡すと、「決まりと違う値で照らした」と出る。決まりとの照合には、既定の値（上の塊）を使う。
- `--max-delay-after-btc-hours` は決まりには無く、既定では判定しない。
- 一覧の作り方（5.1）は人の手による。一覧から投稿を落とせば、その投稿は照らされない。落とした投稿の seq が後の投稿に含まれるなら、後の投稿の時刻で照らされ、遅れが大きく出る。

## 6. 何が示せて、何が示せないか

示せること

- 投稿の時刻（X が ID に入れた時刻）より前に、記録の先頭 N 行がその内容で存在したこと。投稿の時刻は、OpenTimestamps の証明とは別の、運営の外にいる時刻の証人になる。
- 投稿のあとに公開された記録が、先頭 N 行を書き換えていないこと、切り詰めていないこと。

示せないこと

- 投稿より前に、別の記録の系列を作って捨てたことが無いこと。投稿が示すのは、投稿の時点の記録だけである。
  - 最初の投稿（4.2）は、seq 4（2026-10-07 の手順3の取得の後の記録）の時点の鎖を固定する。そのため、seq 1（期間の区切り）と seq 2（閾値と判定期間の候補）を、手順3の取得より前に別の系列から選んでいないことは、この投稿では示せない（T-029 差し戻し1回目の L-1）。seq 1・2 を遅れの判定から外す例外は、このことを変えない。
  - 投稿の決まりが限るのは、recorded_at から投稿までの時間（24時間）だけである。recorded_at は記録した機械の時計による申告なので、記録を実際に作った時刻は限らない（T-029 の監査 L-b）。たとえば、別の系列をいくつも作っておき、選んだ系列の記録の recorded_at を遅く書けば、投稿の決まりの中に収まる。
  - 投稿の決まりから限れるのは次のことである。recorded_at が確定時刻 + 3 時間より後でないこと（5.2）と合わせると、Bitcoin の確定時刻から投稿までは、おおむね24時間 + 3時間を超えない。記録を作ってから stamp するまでの時間は、投稿の決まりでは限れない。それを限るのは、関門の記録の drand の照合（`docs/verify/periods-seal.md` の 7章）である。
  - seq 1〜4 の時刻は、それぞれの `.ots` の Bitcoin の確定時刻で上から押さえられる。それでも、同じ時期に別の系列を作って、別の `.ots` を取っていたことは否定できない。この点は `docs/verify/periods-seal.md` の 7章の「示せないこと」と同じである。
- 投稿が後で消されたり、別の値が投稿されたりしていないこと。X の投稿は、アカウントの持ち主が消せる。短い時間なら編集もできる。照らす人は、投稿の編集の履歴と、第三者のアーカイブも合わせて見る（5.1）。
- 投稿の時刻を、X の外の証人で確かめること。ID から計算した時刻は X が付けたもので、X を信じる範囲でだけ使える（4.3）。
- 記録の中身（`kind`・`note`・`targets`）の正しさ。それは `docs/verify/periods-seal.md` の手順で確かめる。

## 7. 投稿する時機（投稿の決まり。2026-10-08 オーナー決定）

1. 最初の投稿：2026-10-07T18:24:30.169Z に、seq 4 の時点の鎖（seq 1〜4）を投稿した（4.2）。seq 1・2 は決まりの前の例外、seq 3・4 は決まりの中である（5章）。
2. そのあとは、新しい封印の記録を書き足すたびに、その記録の recorded_at から24時間以内に投稿する。投稿するのはアカウント @Dstickchart だけである。手順は次のとおり。
   1. 記録を追記する。
   2. stamp で `.ots` を作る。
   3. コミットする。
   4. `post_text.py` で投稿文を作り、投稿する。
   - 書き足した記録は、すべて24時間以内に投稿される必要がある。後の seq の投稿は、前の seq の行も固定する。そのため、24時間のうちに二つ以上を書き足した場合は、最初に書き足した記録の recorded_at から24時間以内に、最後の seq を投稿すればよい。seq ごとに投稿してもよい（前の seq の文は `post_text.py --seq N` で作る）。
   - Bitcoin での確定は待たない（`pending` のまま投稿してよい）。投稿そのものが、運営の外にいる時刻の証人になるため。確定は、あとで `.bitcoin.ots` として記録に残る。
3. 関門の記録（`threshold-access`、`method-access`、今後の前向きの予言の週ごとの封印）は、24時間を待たずに、追記してすぐに投稿するのがよい。関門の前の鎖を早く固定するほど、関門のあとで前の記録を差し替えられる時間が短くなるため。
4. 投稿ごとに、その投稿を第三者のアーカイブにも保存することを提案する。投稿が消されても照らせるようにするため。保存先と手順はこの文書の範囲の外なので、別のタスクとしてリードに提案する。
5. 投稿の前に、`post_text.py` の止まる条件（1章）に当たらないことを確かめる。手で文を直さない。直したくなったら、`post_text.py` を直すタスクにする。
