# 報道量の数え方の候補と、候補から一つを選ぶ基準（T-028。順番1b で封印する提案）

仮の名前：counting-v1。正式な版の番号ではない。

## オーナーに承認をお願いすること

数え方とは、タグ（テーマ）の1日の報道量 r(d) を「何を何で割るか」の決め方です。オーナーの以前の決定で、数え方は試運転のあとに決めます。ただし、試運転のデータを見てから自由に選ぶと、都合のよい数え方を選べてしまいます。そこで、次のものを試運転より前（method-access より前）に封印します（順番1b。`docs/stats/tags-naive.md` 0章の B）。

1. **数え方の候補の一覧（6つ。2章の表）**
   - 分子は3通り：そのテーマが付いた記事の数（V1 の欄）、そのテーマが付いた記事の数（V2 の欄）、そのテーマが記事の中で言及された回数（V2 の欄）。
   - 分母は2通り：「全体の記事の数」か、「全体の、分子と同じ数え方の合計」（すべての話題について足した量）。
   - 3 × 2 で6つです。翻訳の記事は、どの候補でも数えません（1章）。どの候補も、収集係の日の集計の欄から計算できることを、テストで確かめました。
2. **二つの分母の違い（判断していただきたい点）**。データ源の側で起きうる変化を三つに分けると、二つの分母は次のように振る舞います（`tests/stats/test_counting.py` の `TestDenominatorChanges` で、作り物のデータで確かめました）。
   - (ア) 収集元が増えて、記事が全体に増える：**どちらの分母でも**、タグの比率は変わりません。
   - (イ) データ源が、どの話題も一律に付けやすくなる（記事の数は同じで、1記事に付く話題が全体に増える）：「記事の数」で割ると、すべてのタグの比率が一緒に上がります。「同じ数え方の合計」で割ると、打ち消されて変わりません。
   - (ウ) データ源が、ある話題を新しく付け始める、またはある話題を付けるのをやめる：「同じ数え方の合計」で割ると、その話題と関係のないすべてのタグの比率が一緒に動きます（付け始めれば下がり、やめれば上がる）。「記事の数」で割ると、ほかのタグは動きません。
   - すべてのタグが一緒に上がると、見かけの島が一度にたくさん出ます。一緒に下がると、本当の島を見落としやすくなります。
   - CLAUDE.md は (ウ) が起きることを前提にしています（「途中で消えたテーマ」「データ源がそのテーマを付けるのをやめたのか」「期間の途中や後に生まれたテーマ」）。(イ) が起きるかどうかは、プロジェクトの記録にはありません。
   - 「記事の数」で割るなら、CLAUDE.md の「同じ時間帯の全体の報道量」は「全体の記事の数」と読むことになります。この読みでよいかも、あわせて確かめてください。
3. **基準の案の一覧（5つ。3章の表。採らなかった案も含めて封印・公開します）**
   - B1：二つのテーマの欄（V1 と V2）のうち、テーマが一つも付かない記事が少ない方の欄を使う。記事の数で数え、「同じ数え方の合計」で割る。
   - B2：欄の選び方は B1 と同じ。「全体の記事の数」で割る。
   - B3：データを見ずに C1（V1 の記事の数 ÷ 全体の記事の数）に決め打ちする。
   - B4：1記事あたりのテーマの数が3日のあいだで1割を超えて揺れれば「同じ数え方の合計」で割り、揺れなければ「全体の記事の数」で割る。
   - B5：V2 の言及の回数が記事の数より5%を超えて多ければ、言及の回数で数える。多くなければ記事の数で数える。
   - どの案も、入力は3日分（2015-03-02・03・04）の集計だけで、タグの一覧の件数や中身は見ません。入力・出力・同点のとき・該当なしのときを決めた規則で、`src/stats/counting.py` のコードとしても書きました。
4. **正式に使う基準を一つ**：統計係のおすすめは **B2** です（前回の提出では B1 でしたが、2 の (ウ) の振る舞いを踏まえて変えました。理由は3章 (3)）。2 で (イ) の方を重く見る場合は B1 になります。正式な結果（採点の対象）はこの一つだけで、ほかの基準の案と候補の結果は「比べるための参考で、正式ではない」として並べて公開します。
5. **うまくいかなかったときの行き先（4章の表。これも今のうちに決めて封印します）**
   - 基準が「該当なし」になったら：決めた順（C1、C3、C2、C4、C5、C6）で、計算できる最初の候補を使う。
   - 試しの run の集計が使えないとき（ファイルが記録と合わない、試しの run が終わらないまま正式な run が始まった、試しの run が無い、など）：正式な run の同じ3日の集計を代わりに使う。
   - 試しの run がまだ終わっておらず、正式な run も始まっていないとき：待つ。
   - 封印係が自分で計算し直した結果を正とする。
   - それでも決まらないとき（正式な run の3日分も使えない）だけ、新しい版の順番1b に進む（オーナーの判断が要る）。

承認していただいたあと、正式な基準をコード（`OFFICIAL_CRITERION`）とこの文書に書き入れる作業は、別のタスクで行います。それまでは「未決（undecided）」で、未決のままでは封印しません。

また、試しの run の作りを変える収集係（と封印係）の別のタスク（T-028 の監査の中2。4章 (4)）が合格するまで、順番1b は封印しません（`docs/stats/seal-order1.md` 3章 (3)）。

## 1. 前提

- r(d) の分子と分母の数え方は、収集係の日の集計（`src/collector/gkg.py` 6章。`serialize_day` が書く。頭の行は `# gkg-day 2 <日> <mode>`）から計算できるものに限る（`docs/stats/seal-order1.md` 3章 (3) の監査の申し送り）。行単位の GKG は保存されないので、集計に無い量は、どの候補にも使えない。
- 集計の中で、候補と基準が読む行は次の5種類だけ（`gkg.py` の `serialize_day` と `add_line` を読んで確かめた）。
  - `V id theme`：その日に出たテーマの名前と、その日の中だけの番号。
  - `D g docs`：組 g の文書の数。行の時刻が区画の中で、欄の数と ID の形が合う行だけを数える。テーマが一つも付かない文書も含む。
  - `T g theme_id v1_docs v2_docs v2_mentions`：組 g とテーマの、V1THEMES にそのテーマがある文書の数、V2ENHANCEDTHEMES にある文書の数、V2ENHANCEDTHEMES での言及の回数（同じ文書で複数回なら回数分）。
  - `S name value`：行の件数の内訳。`docs_without_v1_theme`（V1THEMES にテーマが一つも無い文書の数）と `docs_without_v2_theme`（V2 も同じ）。**S の行は組ごとに分かれていない**（すべての組の合計）。
  - 頭の行：形式の版と、日と、mode（trial・official）。
- 組 g は、V2SOURCECOLLECTIONIDENTIFIER の値（1〜2桁の数字。形が違えば `X`）に、翻訳の印があれば `T` を付けたもの（`gkg.py` 4章）。
- **翻訳の記事は数えない**。どの候補も、最後の文字が `T` の組（`1T`、`XT` など）を、分子にも分母にも入れない。形の違う `X` は数える（ID と欄の数は合っていて、文書として数えられたものなので）。出どころは `git show 4e7c511b9469e86bc796b4eb132320a15fdaa5af:reviews/T-016.md`（同じ見出しの節が3つあるので、見出しではなく行で示す）。次の二つを分けて示す（T-028 差し戻し1回目 軽2）。
  - オーナーの発言（原文）：行の全体が `> 翻訳の記事については案aで良いです` と一致する行（ちょうど1つ。統計係が確かめた時点では67行目）。発言には案a の中身が無い。
  - 案a の中身（リードの理解。オーナーの発言ではない）：その3行あとの、行の全体が `- v0 では、翻訳の記事（外国語の報道）を使わない。「外国語の報道は数えていない」ことを、限界として公開物に明記する。` と一致する行（70行目）。案a を尋ねたときの問いの文は、reviews/ に記録が無い。翻訳の印の付いた組を数えないことは、このリードの理解による。
- 組の番号の意味（どの番号がどの種類の収集元か）で組を絞る候補は作らない。番号の意味をこのプロジェクトの文書に記録しておらず、統計係の記憶で決めることになるため。
- 件数はすべて0以上の整数になる（`tagrules.build_tag_list()` の入力の条件。`tags-naive.md` 1章 (2)）。

### (1) 候補に入れなかった数え方（集計の形から計算できないもの）
- **テーマが一つでも付いた記事の数を分母にする**：組ごとの値が集計に無い（S の `docs_without_v1_theme` は、翻訳の組も含むすべての組の合計）。翻訳の組を除いて計算できないので入れない。
- **V1 の言及の回数**：収集係は V1THEMES を文書ごとに重なりを除いた集合として数えている（`add_line` の `s1`）。V1 の言及の回数は集計に無い。
- **同じ記事の重なり（転載・同じ URL）をまとめる数え方**：記事の URL と媒体の名前は、ディスクに書く前に捨てている（`gkg.py` 4章）。集計からはまとめられない。行の時刻がファイルの時刻と違う行（`rows_id_time_differs`）も、組ごとに分けて除けない。
- **翻訳の記事を数える数え方**：オーナーの決定（案a。中身は1章の出どころ）で使わない。

## 3. 候補から一つを選ぶ基準の案

### (1) 共通の決まり
- **入力**：3日分の日の集計（2015-03-02、2015-03-03、2015-03-04。`gkg.TRIAL_DAYS` と同じ）。どの run の集計にするかは4章の規則で一つに決まる。3日がこの順にそろっていなければ止まる（`CountingError`）。
- **出力**：候補の識別子ちょうど一つ。基準そのものが該当なしなら、**代わりの候補**として `FALLBACK_ORDER`（C1、C3、C2、C4、C5、C6）の順で、入力で使える最初の候補にする（`fallback_candidate()`。T-028 差し戻し1回目 中3）。代わりの候補も無ければ、その入力は使えないものとして4章の次の段へ進む。
- **使えるかの確かめ（usable）**：その候補が、3日のどの日でも、分母 > 0 かつ分子の和 > 0 であること。
- 比べるのは分数（`fractions.Fraction`）で、丸めは入れない。
- どの案も、引数は3日分の集計だけで、タグの一覧（件数も中身も）を受け取らない（`test_criteria_do_not_take_tag_list`）。
- 当てはめのコードは `counting.apply_all()`。すべての案を当てはめ、各案の結果に、基準の出力（`candidate`）と、代わりを含めて決まった候補（`decided`）を書き、正式な基準の結果に `official: true` を付ける。
- 代わりの順の理由：記事の数で数える候補（C1〜C4）を先にし、その中では分母が全体の記事の数のもの（C1・C3）を先にする（3章 (3) と同じ理由）。V1 と V2 の順は、同点のときの決まり（V1）にそろえた。

### (2) 各案の考え方（平易な説明）
- **B1・B2**：V1 と V2 は、どちらも記事に付いたテーマの欄で、どちらからも記事の数を数えられる。どちらを使うかを、試しの run で分かる「テーマが一つも付かない記事の数」で決める。この決め方は、下の (3) の仮定A を置いたときに意味を持つ。
- **B3**：データを見ずに、最も素直な読み（ある話題の記事の数を、全体の記事の数で割る）に決める。試運転のデータは、計算できるかの確かめにだけ使う。
- **B4**：全体の記事の数で割る場合、1記事あたりに付くテーマの数が一律に変わると、どのテーマの比率も一緒に動く（冒頭の (イ)）。3日のあいだでもその揺れが大きければ、同じ数え方の合計で割る。
- **B5**：言及の回数が記事の数とほとんど同じなら、言及の回数で数える意味は小さいので記事の数にする。はっきり多ければ、話題の扱いの大きさを表す言及の回数を使う。

### (3) 統計係のおすすめ：B2（理由を前提 → 結論で書く。T-028 差し戻し1回目で B1 から変えた）
1. 単位（記事の数か、言及の回数か）
   - 前提1：`tags-naive.md` 1章 (2) の K = 10 の根拠（7日で70件を超える報道を島とみなす根拠）は、記事の数で数える場合の話で、言及の回数で数えると弱くなる、と書いてある。
   - 前提2：K は順番1で封印し、変えない。
   - 結論：単位は記事の数にする（C1〜C4 の中から選ぶ）。B5 は言及の回数（C6）を選びうるので、おすすめにしない。
2. 分母（全体の記事の数か、同じ数え方の合計か）
   - 前提3（`TestDenominatorChanges` で確かめた）：(ア) 収集元が増えて記事が全体に増える変化は、どちらの分母でも比率を変えない。(イ) どのテーマも一律に付きやすくなる変化は、全体の記事の数で割るとすべてのタグの比率を一緒に動かし、同じ数え方の合計で割ると動かさない。(ウ) あるテーマが付き始める・付かなくなる変化は、同じ数え方の合計で割るとほかのすべてのタグの比率を一緒に動かし、全体の記事の数で割ると動かさない。
   - 前提4：CLAUDE.md は (ウ) が起きることを前提に規則を書いている（「途中で消えたテーマも一覧に残し」「報道が途絶えたのか、データ源がそのテーマを付けるのをやめたのかは、データからは区別できない」「期間の途中や後に生まれたもの」）。(イ) が起きたという記録や前提は、プロジェクトの文書に無い。
   - 前提5：すべてのタグの比率が一緒に動くと、島の判定（普段の水準の何倍か）では、見かけの島が一度に出るか、本当の島を一度に見落とす。どちらも予言の成績を、データ源の都合で動かす。
   - 結論：前提3・4 から、プロジェクトが起きると見込んでいる変化（ウ）で、すべてのタグを一緒に動かさないのは、全体の記事の数で割る分母（C1・C3）である。前提5 から、これを選ぶ。B1・B4・B5 は同じ数え方の合計で割る候補を選びうるので、おすすめにしない。
   - 残る弱み：(イ) が起きた場合は、全体の記事の数で割るとすべてのタグが一緒に動く。(イ) が起きたかは、順番5で公開する候補ごとの結果（C1 と C2 の並べ比べ）で読み手が確かめられる。
   - 前回の提出の理由（同じ数え方の合計なら、CLAUDE.md の二つの理由の両方を除ける）は誤りだったので取り下げる。二つの分母は、除ける変化の種類が違うだけで、片方が両方を除けるわけではない（T-028 の監査の中1）。
3. 欄（V1 か V2 か）
   - 前提6：V1 と V2 のどちらがよいかを、データを見ずに決める根拠を統計係は持っていない（記憶にあるデータ源の説明に頼ることになる）。
   - 仮定A（データでは確かめられない）：テーマが一つも付かない記事の多くは、話題の無い記事ではなく、その欄が話題を付けそこねた記事である。
   - 前提7：「テーマが一つも付かない記事の数」は、3日分の集計で分かるデータ源の性質で、タグの一覧の件数や中身に依らない。
   - 結論：仮定A が成り立つなら、テーマの付かない記事が少ない欄の方が、話題の取りこぼしが少ない。よって欄はそれで選ぶ（B2）。
   - 仮定A が成り立たない場合、比べているのは「どちらの欄が何かしらのテーマを多くの記事に付けるか」だけで、取りこぼしの少なさは言えない。その場合、B2 と B3（V1 に決め打ち）の間に、どちらがよいかの根拠は無い。仮定A を受け入れにくいと判断される場合は、B3 を選んでほしい。
4. 3日の揺れで決める案（B4）
   - 前提8：3日のデータで分かる揺れは、手法を作る期間（約6年）の揺れをほとんど表さない。区切りの 11/10 にもデータからの根拠が無い。
   - 結論：B4 はおすすめにしない。
5. 以上の 1・2・3 から、おすすめは B2（出力は C1 か C3）。

### (4) 基準の案に入れなかった考え
次の考えは検討したが、条件（入力・出力・同点・該当なしが決まり、タグの一覧の件数や中身を見ずに当てはめられる規則であること）に合わないか、3日分からは計算できないので、基準の案に入れなかった。
- 候補ごとに作ったタグの一覧の件数が、ある範囲に入る候補を選ぶ：タグの一覧の件数を見るので、条件に合わない。
- 候補ごとの N_med や A の大きさで選ぶ：N_med は手法を作る期間の全体の値で、3日分の入力からは計算できない。3日分の値で代えると、件数に近い量を見て選ぶことになる。
- 比率の日ごとの安定さ（長い期間の分散など）で選ぶ：3日では計算の意味が無い。
- 予言の当たりやすさで選ぶ：手法を作る期間の全体のデータが要り、試運転の段階では計算できない。結果を見て数え方を選ぶことにもなる。

## 4. 基準の入力を一つに決める規則と、止まったあとの行き先

試しの run は、コードを変えると run_id が変わり、別の run としてもう一度行える（`gkg.py` 5.1章）。結果を見てから、どの run の集計を入力にするかを選べないように、入力を次の規則で一つに決める。止まったあとの行き先も、ここで決めて順番1b で一緒に封印する（T-028 差し戻し1回目 中3）。規則のコードは `counting.decide()`（中で `select_trial_input()`・`select_official_input()`・`apply_all()` を使う）と `counting.check_prefix_versions()`。

### (1) 読むもの
- 試しの run のマニフェスト `data/manifest/gdelt-gkg-trial.jsonl` と、正式な run のマニフェスト `data/manifest/gdelt-gkg-method.jsonl`。どちらも、順番2を封印する commit（HEAD、40桁）の版（`git show <HEAD>:<パス>` の標準出力のバイト列。ファイルが無ければ空）を読む。
- **git の確かめ**（封印係が自分のコードで行う）：作業ツリーのファイルが HEAD の版と同じこと。`git log --all --full-history --format=%H -- <パス>` の各 commit の版（ファイルが無い版は空）が、どれも HEAD の版の先頭と同じこと（追記だけ。並び順は使わない）。通らないマニフェストは「使えない」（`decide()` に None を渡す）。

### (2) 段と行き先
| 段 | 入力 | 使う条件 | まだそろっていないとき | 使えないとき |
|---|---|---|---|---|
| 1段目 | 試しの run R の3日の集計。R は、試しの run のマニフェストで行の並びで最初の `run-start` の `run_id`（ほかの試しの run は使わない） | R の run-start が `mode: trial`・`trial: true`・`official: false`。R に `run-complete` がある。R の `day` の行が3日にちょうど一つずつ（ほかの日は無い）、`mode` が `trial`、`file_name` が `gkg-trial-<R>-day-<YYYYMMDD>.tsv.gz`。正式な run の `run-start` があれば、その `trial_run_ids` の最初が R。各ファイルの sha256 が `day` の行と一致し、頭の行の日と mode が合う。正式な基準（代わりの候補を含む）で候補が決まる | 試しの run の `run-start` が無いか、R に `run-complete` が無い：正式な run の `run-start` がまだ無ければ **待つ**（pending）。正式な run の `run-start` があれば、1段目は使えない | 2段目へ |
| 2段目 | 正式な run O の、同じ3日の集計。O は、正式な run のマニフェストの最初の `run-start` の `run_id`（`gkg.official_run_id` と同じ決め方） | O の run-start が `mode: official`・`trial: false`・`official: true`。O の3日の `day` の行がちょうど一つずつ、`mode` が `official`、`file_name` が `gkg-official-<O>-day-<YYYYMMDD>.tsv.gz`。各ファイルの sha256 が一致し、頭の行が合う。候補が決まる（`run-complete` は求めない） | 正式な run の `run-start` が無いか、3日の `day` の行がそろっていない：**待つ**（pending） | **止まる**（stopped）。(3) へ |

- 1段目を待つ期限は、正式な run の `run-start` がマニフェストにコミットされた時点である。時計は使わない。収集係のコードは、正式な run の `run-start` のあとは試しの run を始めない（`gkg.run_gkg`）ので、その時点で R が終わっていなければ、もう終わらない。
- **封印係の計算を正とする**：順番2の結果は、封印係が、順番1b で封印したコード（sha256 が一致するもの）を、(1) の確かめに通ったマニフェストと3日のファイルに自分で当てはめた結果とする。収集係などが示した結果と違っても止めず、違ったことを記録に残す。
- 待つ（pending）のは、データの値を見て決まる条件ではない。待ったあと、同じ順番1b の記録で同じ手順をもう一度行う。何回目かは、封印係の記録の数で分かる。
- 2段目は、1段目と同じ3日の同じ GKG のファイルを、正式な run で取り直したものである（`gkg.py` 5.1章「正式な run は、試しの run の3日も含めて、全部の日を取り直す」）。

### (3) それでも決まらないとき
2段目でも止まった場合（正式な run のマニフェストが git の確かめに通らない、ファイルが記録と合わない、3日分のどれでも使える候補が無い）と、`docs/stats/seal-order1.md` 3章 (2) の時機の条件を満たさない場合だけ、その順番1b の記録では順番2を封印しない。止まった事実を記録して公開し、新しい版の順番1b に進む（`seal-order1.md` 3章 (2)「順番2で止まったあとの扱い」）。

### (4) 「最初の run」にした理由と、残る穴（T-028 の監査の中2）
- 前提1：最初の run-start の行は、試しの run のマニフェストをコミットし、さらにそのコミットが履歴を書き換えられない形（時刻証明。OpenTimestamps など）になったあとは、変えられない。それより前は、コミットを作り直したり、コミットの前に行を消したりできる。
- 前提2：最後の run にすると、集計を見たあとでコードを変えて新しい試しの run を行えば、入力を差し替えられる。
- 前提3：最初の run が途中で止まった場合も、同じコードなら同じ run_id で再開して終えられる（`gkg.py` 5章）。
- 結論：最初の run を使う。最後の run や「終わった run のうち最初のもの」は、前提2 の差し替えの余地を残すので採らない。
- 残る穴：前提1 の「変えられなくなる」時点より前に、運営側は3日分の集計を見て B1〜B5 の結果を計算できる。気に入らなければ、マニフェストの行とファイルを消して（または移して）、別の run_id で取り直せる。今の試しの run の作り（終わったあとにマニフェストをコミットする。`gkg.py` 5.1章）では、統計係の範囲で塞げない。試しの run を2段にするなど作りを変える収集係（と封印係）の別のタスクが要り、その合格を順番1b の封印の前提条件にする（`seal-order1.md` 3章 (3)）。
- 2段目へ進ませる操作（試しの run のファイルを変える、試しの run を終わらせずに正式な run を始める）も運営側が起こせる。2段目の入力は、同じ3日の同じ GKG のファイルを、正式な run のコードで集計したものなので、試しの run と正式な run のコード（run_id）が同じで、取れなかったファイルが同じなら、中身は同じになる。違いうるのは、二つの run の間でコードを変えた場合と、取れなかったファイルが違う場合だけである。二つの run_id と、各日の取れなかったファイル（`day` の行の `failed_files`）は記録に残るので、公開物で並べて示す。

`counting.py apply <試しの run のマニフェスト> <正式な run のマニフェスト> <試しの run の保存先> <正式な run の保存先>` は、(2) を行い、すべての基準の案の結果を出力する（終了コード：決まった 0、止まった 1、待つ 3）。(1) の git の確かめは封印係が行い、通らないマニフェストは `FAILED` と書いて渡す。

## 5. 順番に矛盾が無いことの確かめ

順番は `tags-naive.md` 5章の表と `seal-order1.md` による。

| 段 | 何をするか | 何を読むか |
|---|---|---|
| 順番1 | 除外の規則と入れる規則を封印 | データを読まない |
| 試しの run の作りの直し | 4章 (4) の穴を塞ぐ収集係（と封印係）の別のタスク | データを読まない |
| 順番1b | 候補の一覧（2章）、基準の案と代わりの順（3章）、入力の段と行き先（4章）、正式な基準を封印（このタスクの提案に、オーナーの承認を得たもの） | データを読まない（`counting.py` はデータ無しで定義を出す） |
| method-access | 手法を作る期間のデータへの最初の接触の記録 | — |
| 試しの run | 3日分の集計を作る。入口のスクリプトは、除外の規則の封印と method-access の記録を求める（`src/collector/acquire_gkg.py`） | GKG（3日分） |
| 順番2 | 4章の規則で入力を決め、正式な基準を当てはめ、選ばれた候補を封印 | 試しの run の3日分（使えなければ正式な run の同じ3日） |
| 順番3〜5 | 数え方とのつながり、欠けた日の一覧、タグの一覧の結果（6つの候補すべて） | 正式な run の集計 |

- 順番1b の封印は、基準・代わりの順・入力の段の中身だけを決め、データの値を使わない。値を使うのは順番2で、そのときには全部が封印されている。よって「基準を method-access より前に封印し、当てはめを試しの run のあとに行う」順に矛盾は無い。
- 順番2の結果は、封印したコードと、4章で一つに決まる入力だけで決まる。順番2をいつ行うかで、使う段は変わりうる（正式な run が始まる前は1段目を待つ）が、どの段を使うかはマニフェストの記録だけで決まる。
- 試しの run の集計は、正式な run の結果としては使わない（`gkg.py` 5.1章）。順番2で基準の入力に使うのは、数え方を選ぶためで、タグの一覧や判定には使わない。2段目で正式な run の3日分を基準の入力に使う場合も、使うのは数え方を選ぶためだけである。
- 統計係が確かめた範囲では、矛盾は無かった。4章 (4) の穴は順番の矛盾ではなく、試しの run の作りの穴で、別のタスクで塞ぐ。

## 6. 順番1b の記録に入れるもの（封印係への申し送り）

`docs/stats/seal-order1.md` 3章 (3) の関門に従う。この文書から決まるものは次のとおり。
- 候補の一覧と基準の案のファイル：`docs/stats/counting.md`（この文書）と `src/stats/counting.py`。どちらも sha256 を記録に入れる（関門の2・4・6）。

- 規則のコード：`src/stats/counting.py` の sha256（関門の4。コードで書いた規則。入力の段と行き先の `decide()` も含む）。順番2で、封印係はこの sha256 と一致するコードを自分で実行して当てはめる。

## 7. 限界

- 候補は、収集係の今の集計の形（形式の版 2）から計算できるものだけである。形式の版が変わると `parse_day()` は止まる。試しの run と正式な run の両方で止まれば、4章 (3) に進む。
- 3日は 2015年3月の初めで、手法を作る期間（約6年）のうちの3日だけである。B1・B2 の欄の選び方は、その3日の性質を表すだけで、のちのデータ源の仕様の変化（欄の付け方が変わるなど）は反映しない。
- 4章 (4) の穴（試しの run の最初のコミットと時刻証明より前の差し替え、2段目へ進ませる操作）。
- B1・B2 の値（S の行）は、翻訳の組と `X` を含む（3章 (1)）。
- 仮定A はデータで確かめられない（3章 (3) の3）。
- 「検討した案をすべて」載せたかは、記録からは確かめられない（`seal-order1.md` 3章 (3) の4の限界）。統計係は、検討した案を3章の表と 3章 (4) にすべて書いた。
- B4 の 11/10 と B5 の 21/20 には、データからの根拠が無い。
