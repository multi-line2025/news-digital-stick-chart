# 報道量の数え方の候補と、候補から一つを選ぶ基準（T-028。順番1b で封印する提案）

仮の名前：counting-v1。正式な版の番号ではない。

## オーナーに承認をお願いすること

数え方とは、タグ（テーマ）の1日の報道量 r(d) を「何を何で割るか」の決め方です。オーナーの以前の決定で、数え方は試運転のあとに決めます。ただし、試運転のデータを見てから自由に選ぶと、都合のよい数え方を選べてしまいます。そこで、次のものを試運転より前（method-access より前）に封印します（順番1b。`docs/stats/tags-naive.md` 0章の B）。

### A. 決めていただきたいこと（問いは一つ）

候補の分母は2通りあります。
- **記事の数で割る**：「その話題の記事が、全記事の何%か」。
- **テーマの合計で割る**：データ源は1本の記事にいくつものテーマ（話題の印）を付けます。全テーマについて「付いた記事の数」を足したものを合計とし、「付いたテーマ全体のうち、その話題が何%か」を見ます。

例：ある日の記事が1000本、「天気」のテーマが付いた記事が10本、テーマの合計が5000とします。記事の数で割ると 10 ÷ 1000 = 1%、テーマの合計で割ると 10 ÷ 5000 = 0.2% です。データ源の側で次の変化が起きたとき、天気の比率はこう動きます（作り物のデータで確かめました。`tests/stats/test_counting.py` の `TestDenominatorChanges`）。

| データ源の側の変化 | 記事の数で割る | テーマの合計で割る |
|---|---|---|
| (ア) 収集元が倍に増える（記事2000本、天気20本、合計10000） | 1%。変わらない | 0.2%。変わらない |
| (イ) どの話題も一律に付けやすくなる（記事1000本のまま、天気15本、合計7500） | 1.5%。**上がる** | 0.2%。変わらない |
| (ウ) 新しい話題「X」を付け始め、500本に付いた（記事1000本、天気10本、合計5500） | 1%。変わらない | 約0.18%。**下がる** |

- (ア) で変わらないのは、増えた収集元の話題の割合が前と同じ場合だけです。違う話題の多い収集元が加われば、どちらの分母でも比率は動きます。
- (ウ) の逆に、データ源がある話題を付けるのをやめると、テーマの合計で割った場合は、ほかのすべてのタグの比率が上がります。
- どちらの分母でも、付け始めた・やめた話題そのものの比率は動きます。これは割り算では除けません。
- 表で「上がる」「下がる」となった場合、天気だけでなく、関係のないすべてのタグが同じ割合で一緒に動きます。島の判定は「普段の水準の何倍か」で決まるので、一緒に動く割合が大きいほど、閾値の近くにあったタグが閾値を越えたり（見かけの島）、越えなくなったり（島の見落とし）します。割合が小さければ影響は小さいですが、ゼロにはなりません。GDELT で (イ) と (ウ) がどれくらいの大きさで起きるかは、データを見ないと分かりません。

**CLAUDE.md の目的の句との関係**：CLAUDE.md は、比率にする目的を「収集元のサイト数の増減や、テーマ付与の変化による見かけの変動を除くため」と決めています。前半（収集元の増減）は (ア) で、どちらの分母でも除けます。後半の「テーマ付与の変化」には (イ) と (ウ) の両方が入ります。記事の数で割ると、(ウ) では関係のないタグは動きませんが、(イ) は残ります。テーマの合計で割ると、(イ) は打ち消しますが、(ウ) で関係のないタグが動きます。**どちらの分母でも、割り算で果たせるのは後半の目的の半分だけです。** 残りの半分は、割り算以外のしくみ（普段の水準を過去の一定期間からとること。数え方は未決事項2で確定する。消えたテーマに印を付けること）に頼ることになります。データを見ずに、どちらの分母が優れているとは言えません。統計係は、どちらかをすすめることはしません。

**問い：(イ) と (ウ) のどちらの変化で、関係のないタグが一緒に動かないようにしたいですか。** 答えごとに、正式に使う基準が一つに決まります。

<!-- table:answer -->
| 答え | 正式に使う基準 | 割り算で打ち消すもの | 残るもの |
|---|---|---|---|
| (イ) | `B1` | (ア) と (イ)（テーマの合計で割る） | (ウ) で、関係のないタグが一緒に動く |
| (ウ) | `B2` | (ア)。(ウ) で関係のないタグを動かさない（記事の数で割る） | (イ) で、すべてのタグが一緒に動く |

B1 と B2 の違いは分母だけです。どちらも、二つのテーマの欄（V1 と V2）のうち、テーマが一つも付かない記事が少ない方の欄を使い、記事の数で数えます（3章）。

## 1. 前提

- r(d) の分子と分母の数え方は、収集係の日の集計（`src/collector/gkg.py` 6章。`serialize_day` が書く。頭の行は `# gkg-day 2 <日> <mode>`）から計算できるものに限る（`docs/stats/seal-order1.md` 3章 (3) の監査の申し送り）。行単位の GKG は保存されないので、集計に無い量は、どの候補にも使えない。
- 集計の中で、候補と基準が読む行は次の5種類だけ（`gkg.py` の `serialize_day` と `add_line` を読んで確かめた）。
  - `V id theme`：その日に出たテーマの名前と、その日の中だけの番号。
  - `D g docs`：組 g の文書の数。行の時刻が区画の中で、欄の数と ID の形が合う行だけを数える。テーマが一つも付かない文書も含む。
  - `T g theme_id v1_docs v2_docs v2_mentions`：組 g とテーマの、V1THEMES にそのテーマがある文書の数、V2ENHANCEDTHEMES にある文書の数、V2ENHANCEDTHEMES での言及の回数（同じ文書で複数回なら回数分）。
  - `S name value`：行の件数の内訳。`docs_without_v1_theme`（V1THEMES にテーマが一つも無い文書の数）と `docs_without_v2_theme`（V2 も同じ）。**S の行は組ごとに分かれていない**（すべての組の合計）。
  - 頭の行：形式の版と、日と、mode（trial・official）。
- 組 g は、V2SOURCECOLLECTIONIDENTIFIER の値（1〜2桁の数字。形が違えば `X`）に、翻訳の印があれば `T` を付けたもの（`gkg.py` 4章）。
- **翻訳の記事は数えない**。どの候補も、最後の文字が `T` の組（`1T`、`XT` など）を、分子にも分母にも入れない。形の違う `X` は数える（ID と欄の数は合っていて、文書として数えられたものなので）。出どころは `git show 4e7c511b9469e86bc796b4eb132320a15fdaa5af:reviews/T-016.md`（同じ見出しの節が3つあるので、見出しではなく行で示す）。次の二つを分けて示す（T-028 差し戻し1回目 軽2）。
  - オーナーの発言（原文）：行の全体が `> 翻訳の記事については案aで良いです` と一致する行（ちょうど1つ。統計係が確かめた時点では67行目）。発言には案a の中身が無い。
  - 案a の中身（リードの理解。オーナーの発言ではない）：その3行あとの、行の全体が `- v0 では、翻訳の記事（外国語の報道）を使わない。「外国語の報道は数えていない」ことを、限界として公開物に明記する。` と一致する行（70行目）。案a を尋ねたときの問いの文は、reviews/ に記録が無い。翻訳の印の付いた組を数えないことは、このリードの理解による。
- 組の番号の意味（どの番号がどの種類の収集元か）で組を絞る候補は作らない。番号の意味をこのプロジェクトの文書に記録しておらず、統計係の記憶で決めることになるため。
- 件数はすべて0以上の整数になる（`tagrules.build_tag_list()` の入力の条件。`tags-naive.md` 1章 (2)）。

### (1) 候補に入れなかった数え方（集計の形から計算できないもの）
- **テーマが一つでも付いた記事の数を分母にする**：組ごとの値が集計に無い（S の `docs_without_v1_theme` は、翻訳の組も含むすべての組の合計）。翻訳の組を除いて計算できないので入れない。

- **同じ記事の重なり（転載・同じ URL）をまとめる数え方**：記事の URL と媒体の名前は、ディスクに書く前に捨てている（`gkg.py` 4章）。集計からはまとめられない。行の時刻がファイルの時刻と違う行（`rows_id_time_differs`）も、組ごとに分けて除けない。
- **翻訳の記事を数える数え方**：オーナーの決定（案a。中身は1章の出どころ）で使わない。

## 3. 候補から一つを選ぶ基準の案

### (1) 共通の決まり
- **入力**：3日分の日の集計（2015-03-02、2015-03-03、2015-03-04。`gkg.TRIAL_DAYS` と同じ）。どの run の集計にするかは4章の規則で一つに決まる。3日がこの順にそろっていなければ止まる（`CountingError`）。
- **出力**：候補の識別子ちょうど一つ。基準そのものが該当なしなら、**代わりの候補**として、下の表のその基準の順で、入力で使える最初の候補にする（`fallback_candidate()`。T-028 差し戻し1回目 中3）。
- **使えるかの確かめ（usable）**：その候補が、3日のどの日でも、分母 > 0 かつ分子の和 > 0 であること。6つの候補のどれも使えなければ、その入力では決まらないので止まる（4章）。
- 比べるのは分数（`fractions.Fraction`）で、丸めは入れない。
- どの案も、引数は3日分の集計だけで、タグの一覧（件数も中身も）を受け取らない（`test_criteria_do_not_take_tag_list`）。
- 当てはめのコードは `counting.apply_all()`。すべての案を当てはめ、各案の結果に、基準の出力（`candidate`）と、代わりを含めて決まった候補（`decided`）を書き、正式な基準の結果に `official: true` を付ける。

- B1・B2 の u1・u2・n は、S の行が組ごとに分かれていないので、翻訳の組（`T` の付いた組）と `X` も含む（1章）。翻訳の流れは取得していないので、英語の流れの中の翻訳の印の付いた行だけが入る（`gkg.py` 1章によれば、ほとんど無い見込み）。欄を比べるための値で、候補の計算には使わない。
- B4 の 11/10 と B5 の 21/20 は、データを見ずに決めた値である（根拠は「1割」「5%」という区切りのよさだけで、データからの根拠は無い）。

### (2) 各案の考え方（平易な説明）
- **B1・B2**：V1 と V2 は、どちらも記事に付いたテーマの欄で、どちらからも記事の数を数えられる。どちらを使うかを、3日分で分かる「テーマが一つも付かない記事の数」で決める。この決め方は、下の (3) の仮定A を置いたときに意味を持つ。B1 と B2 の違いは分母だけである（冒頭の A）。
- **B3**：データを見ずに、最も素直な読み（ある話題の記事の数を、全体の記事の数で割る）に決める。データは、計算できるかの確かめにだけ使う。
- **B4**：記事の数で割る場合、1記事あたりに付くテーマの数が一律に変わると、どのテーマの比率も一緒に動く（冒頭の (イ)）。3日のあいだでもその揺れが大きければ、テーマの合計で割る。
- **B5**：言及の回数が記事の数とほとんど同じなら、言及の回数で数える意味は小さいので記事の数にする。はっきり多ければ、話題の扱いの大きさを表す言及の回数を使う。

### (3) 案の性質（前提 → 結論。統計係は、どの案もすすめない）
正式に使う基準は、冒頭の A の問いの答えで B1 か B2 に決まる。ここでは、各案の性質を書く。
1. 単位（記事の数か、言及の回数か）
   - 前提1：`tags-naive.md` 1章 (2) の K = 10 の根拠（7日で70件を超える報道を島とみなす根拠）は、記事の数で数える場合の話で、言及の回数で数えると弱くなる、と書いてある。
   - 前提2：K は順番1で封印し、変えない。
   - 結論：B1・B2 は記事の数で数える（C1〜C4 から選ぶ）。B5 は言及の回数（C6）を選びうるので、K の根拠が弱くなる場合がある。
2. 分母（記事の数か、テーマの合計か）
   - 前提3（冒頭の表。`TestDenominatorChanges` で確かめた）：割り算で打ち消せるのは、記事の数で割ると (ア) だけ、テーマの合計で割ると (ア) と (イ)。テーマの合計で割ると、(ウ) で関係のないタグを一緒に動かす。
   - 前提4：CLAUDE.md の目的の句の後半「テーマ付与の変化」には (イ) と (ウ) の両方が入る。
   - 前提5：GDELT で (イ) と (ウ) がどれくらいの大きさで起きるかは、データを見ないと分からない（統計係はデータを見ていない。記憶にあるデータ源の説明には頼らない）。
   - 結論：前提3・4 から、どちらの分母でも、割り算で果たせるのは後半の目的の半分である。前提5 から、どちらが優れているかはデータを見ずに言えない。よって、どちらにするかは、冒頭の A の問い（(イ) と (ウ) のどちらで関係のないタグを動かしたくないか）で決める。
3. 欄（V1 か V2 か。B1・B2 に共通）
   - 前提6：V1 と V2 のどちらがよいかを、データを見ずに決める根拠を統計係は持っていない（記憶にあるデータ源の説明に頼ることになる）。
   - 仮定A（データでは確かめられない）：テーマが一つも付かない記事の多くは、話題の無い記事ではなく、その欄が話題を付けそこねた記事である。
   - 前提7：「テーマが一つも付かない記事の数」は、3日分の集計で分かるデータ源の性質で、タグの一覧の件数や中身に依らない。
   - 結論：仮定A が成り立つなら、テーマの付かない記事が少ない欄の方が、話題の取りこぼしが少ない。B1・B2 は欄をそれで選ぶ。
   - 仮定A が成り立たない場合、比べているのは「どちらの欄が何かしらのテーマを多くの記事に付けるか」だけで、取りこぼしの少なさは言えない。その場合、欄の選び方に根拠は無く、決め打ちの B3（記事の数で割る）と B2 の間にも、どちらがよいかの根拠は無い。
4. 3日の揺れで決める案（B4）
   - 前提8：3日のデータで分かる揺れは、手法を作る期間（約6年）の揺れをほとんど表さない。区切りの 11/10 にもデータからの根拠が無い。
   - 結論：B4 の分母の選び方は、3日の偶然の揺れで決まりうる。

### (4) 基準の案に入れなかった考え
次の考えは検討したが、条件（入力・出力・同点・該当なしが決まり、タグの一覧の件数や中身を見ずに当てはめられる規則であること）に合わないか、3日分からは計算できないので、基準の案に入れなかった。
- 候補ごとに作ったタグの一覧の件数が、ある範囲に入る候補を選ぶ：タグの一覧の件数を見るので、条件に合わない。
- 候補ごとの N_med や A の大きさで選ぶ：N_med は手法を作る期間の全体の値で、3日分の入力からは計算できない。3日分の値で代えると、件数に近い量を見て選ぶことになる。
- 比率の日ごとの安定さ（長い期間の分散など）で選ぶ：3日では計算の意味が無い。
- 予言の当たりやすさで選ぶ：手法を作る期間の全体のデータが要り、試運転の段階では計算できない。結果を見て数え方を選ぶことにもなる。

## 4. 基準の入力を一つに決める規則と、止まったあとの行き先

試しの run は、コードを変えると run_id が変わり、別の run としてもう一度行える（`gkg.py` 5.1章）。結果を見てから、どの run の集計を入力にするかを選べないように、入力を次の規則で一つに決める。止まったあとの行き先も、ここで決めて順番1b で一緒に封印する。規則のコードは `counting.decide()`（中で `select_trial_input()`・`select_official_input()`・`apply_all()` を使う）と `counting.check_prefix_versions()`。

### (1) 読むもの
- 試しの run のマニフェスト `data/manifest/gdelt-gkg-trial.jsonl` と、正式な run のマニフェスト `data/manifest/gdelt-gkg-method.jsonl`。どちらも、順番2を封印する commit（HEAD、40桁）の版（`git show <HEAD>:<パス>` の標準出力のバイト列。ファイルが無ければ空）を読む。
- **git の確かめ**（封印係が自分のコードで行う）：作業ツリーのファイルが HEAD の版と同じこと。`git log --all --full-history --format=%H -- <パス>` の各 commit の版（ファイルが無い版は空）が、どれも HEAD の版の先頭と同じこと（追記だけ。並び順は使わない）。どちらかのマニフェストが通らなければ止まる（`decide()` に None を渡す）。

### (2) 手順と行き先（`decide()`。T-028 差し戻し2回目 中-B1・中-B2 で直した）
R は、試しの run のマニフェストで行の並びで最初の `run-start` の `run_id`。ほかの試しの run は使わない。

| 順 | 確かめること | 満たさないとき |
|---|---|---|
| 1 | 二つのマニフェストが (1) の git の確かめに通る。JSON として読め、最初の `run-start` が決まった形（試しの run は `mode: trial`・`trial: true`・`official: false`、正式な run は `mode: official`・`trial: false`・`official: true`） | 止まる |
| 2 | 正式な run の `run-start` があれば：試しの run のマニフェスト（HEAD の版）の sha256 が、その `trial_manifest_sha256` と一致する（空のマニフェストなら `null`）。`trial_run_ids` の最初の要素が R（試しの run が無ければ一覧が空） | 止まる |
| 3 | R に `run-complete` がある（試しの run の `run-start` が無い場合も、ここで「無い」とする） | 正式な run の `run-start` が無ければ **待つ**。あれば：試しの run の `run-start` が一つも無いか、`run-start` が R の一つだけで R に `day` の行が一つも無ければ **2段目**へ（6）。それ以外（R に `day` の行がある、試しの run の `run-start` が二つ以上ある）は止まる |
| 4 | R の `day` の行が3日にちょうど一つずつ（ほかの日は無い）、`mode` が `trial`、`file_name` が `gkg-trial-<R>-day-<YYYYMMDD>.tsv.gz` | 止まる |
| 5 | 3日のファイルがあり、sha256 が `day` の行と一致し、頭の行の日と mode が合う。6つの候補のどれかが使える。→ **1段目で決まる** | 止まる |
| 6 | 2段目：正式な run（最初の `run-start` の run。`gkg.official_run_id` と同じ決め方）の3日の `day` の行がそろっている（`run-complete` は求めない） | そろっていなければ **待つ**。形が違えば止まる |
| 7 | 2段目の3日のファイルが 5 と同じ確かめに通り、どれかの候補が使える。→ **2段目で決まる** | 止まる |

- **2段目に進むのは、正式な run が始まっていて、試しの run の `run-start` が一つも無いか、試しの run の `run-start` が R の一つだけで、R に `day` の行が一つも無い場合だけ**である（T-028 差し戻し3回目 中-3）。どちらの場合も、試しの run の集計は1日分も無いので、運営側は試しの run の結果を見ていない。試しの run を二つ行い（たとえば R を途中で止め、別の run で3日を全部作る）、その結果を見てから正式な run を始めて2段目にする、という選び方は、止まるので使えない。
- 正式な run の開始までに R が終わったかは、2 で、正式な run の `run-start` に書かれた試しの run のマニフェストの sha256 と、今のマニフェストが同じであることで確かめる。開始のあとで `run-complete` の行を書き足すと、2 で止まる（中-B1）。
- ファイルが無い・中身が記録と違う・記録が書き換えられた・`trial_run_ids` が合わない、は運営側が起こせることなので、代わりのものに進まず止まる。止まれば、その順番1b の記録では順番2を封印できず、止まったことが公開される。
- **封印係の計算を正とする**：順番2の結果は、封印係が、順番1b で封印したコード（sha256 が一致するもの）を、(1) の確かめに通ったマニフェストと3日のファイルに自分で当てはめた結果とする。ほかの者が示した結果と違っても止めず、違ったことを記録に残す。
- 待つ（pending）は、データの値を見て決まる条件ではない。待ったあと、同じ順番1b の記録で同じ手順をもう一度行う。待った回数を第三者が数えられるように、封印係が順番2を試みるたびに、結果（待つを含む）を ledger に記録することを提案する（封印係の範囲。記録の形は封印係が決める）。記録しなければ、待った回数は第三者には分からない（7章）。
- **出力と記録に入れるもの**：決まったか・待つか・止まったか、通った手順と止まった理由（`steps`）、使った段と run_id、3日のファイルの名前と sha256、すべての基準の案の結果、そして**二つの run（試しの run R と正式な run）の run_id と、両方の run の3日の `failed_files`**（`runs`。マニフェストの `day` の行から写す。run の `run-start` が無ければ run_id と failed_files は `null`。`day` の行がまだ無い日は載せない。`day` の行の failed_files が空の一覧なら `[]`、`day` の行に failed_files の項目が無ければ `null`）。

### (3) それでも決まらないとき
(2) で止まった場合と、`docs/stats/seal-order1.md` 3章 (2) の時機の条件を満たさない場合は、その順番1b の記録では順番2を封印しない。止まった事実を記録して公開し、新しい版の順番1b に進む（`seal-order1.md` 3章 (2)「順番2で止まったあとの扱い」）。

### (4) 「最初の run」にした理由と、残る穴
- 前提1：最初の run-start の行は、試しの run のマニフェストをコミットし、さらにそのコミットが履歴を書き換えられない形（時刻証明。OpenTimestamps など）になったあとは、変えられない。それより前は、コミットを作り直したり、コミットの前に行を消したりできる。
- 前提2：最後の run にすると、集計を見たあとでコードを変えて新しい試しの run を行えば、入力を差し替えられる。
- 前提3：最初の run が途中で止まった場合も、同じコードなら同じ run_id で再開して終えられる（`gkg.py` 5章）。
- 結論：最初の run を使う。最後の run や「終わった run のうち最初のもの」は、前提2 の差し替えの余地を残すので採らない。
- **順番2を行う時機**：(2) では、1段目か2段目か止まるかは、正式な run の開始のときの試しの run のマニフェストの中身（2 で確かめる）だけで決まる。1段目の記録とファイルがそろったあとは、いつ行っても1段目で決まり、ファイルを壊せば止まる。よって、順番2をいつ行うかで、使う段を選ぶことはできない。
- 残る穴（T-028 の監査の中2）：前提1 の「変えられなくなる」時点より前に、運営側は3日分の集計を見て B1〜B5 の結果を計算できる。気に入らなければ、マニフェストの行とファイルを消して（または移して）、別の run_id で取り直せる。試しの run を途中で止めて終わらせないまま正式な run を始める操作や、試しの run を二つ以上行う操作は、(2) で止まる（差し戻し3回目 中-3）。止まれば、そのことが公開され、その順番1b の記録では順番2を封印できない。残るのは、マニフェストの最初のコミットと時刻証明より前に、行とファイルを消して取り直す操作で、今の試しの run の作りでは、統計係の範囲で塞げない。試しの run を2段にするなど作りを変える収集係（と封印係）の別のタスクが要り、その合格を順番1b の封印の前提条件にする（`seal-order1.md` 3章 (3)）。
- 2段目の入力は、同じ3日の同じ GKG のファイルを、正式な run のコードで集計したものである（`gkg.py` 5.1章「正式な run は、試しの run の3日も含めて、全部の日を取り直す」）。試しの run と正式な run のコード（run_id）が同じで、取れなかったファイルが同じなら、中身は同じになる。違いうるのは、二つの run の間でコードを変えた場合と、取れなかったファイルが違う場合だけである。そのため、二つの run_id と、両方の run の3日の `failed_files` を出力と記録に入れ、公開物で並べて示す。

`counting.py apply <試しの run のマニフェスト> <正式な run のマニフェスト> <試しの run の保存先> <正式な run の保存先>` は、(2) を行い、すべての基準の案の結果を出力する（終了コード：決まった 0、止まった 1、待つ 3）。(1) の git の確かめは封印係が行い、通らないマニフェストは `FAILED` と書いて渡す。

## 5. 順番に矛盾が無いことの確かめ

順番は `tags-naive.md` 5章の表と `seal-order1.md` による。

| 段 | 何をするか | 何を読むか |
|---|---|---|
| 順番1 | 除外の規則と入れる規則を封印 | データを読まない |
| 試しの run の作りの直し | 4章 (4) の穴を塞ぐ収集係（と封印係）の別のタスク | データを読まない |
| 順番1b | 候補の一覧（2章）、基準の案と代わりの順（3章）、入力の手順と行き先（4章）、正式な基準を封印（このタスクの提案に、オーナーの承認を得たもの） | データを読まない（`counting.py` はデータ無しで定義を出す） |
| method-access | 手法を作る期間のデータへの最初の接触の記録 | — |
| 試しの run | 3日分の集計を作る。入口のスクリプトは、除外の規則の封印と method-access の記録を求める（`src/collector/acquire_gkg.py`） | GKG（3日分） |
| 順番2 | 4章の規則で入力を決め、正式な基準を当てはめ、選ばれた候補を封印 | 試しの run の3日分（4章 (2) の場合だけ正式な run の同じ3日） |
| 順番3〜5 | 数え方とのつながり、欠けた日の一覧、タグの一覧の結果（6つの候補すべて） | 正式な run の集計 |

- 順番1b の封印は、基準・代わりの順・入力の手順の中身だけを決め、データの値を使わない。値を使うのは順番2で、そのときには全部が封印されている。よって「基準を method-access より前に封印し、当てはめを試しの run のあとに行う」順に矛盾は無い。
- 試しの run の集計は、正式な run の結果としては使わない（`gkg.py` 5.1章）。順番2で基準の入力に使うのは、数え方を選ぶためで、タグの一覧や判定には使わない。2段目で正式な run の3日分を基準の入力に使う場合も、使うのは数え方を選ぶためだけである。
- 統計係が確かめた範囲では、矛盾は無かった。4章 (4) の穴は順番の矛盾ではなく、試しの run の作りの穴で、別のタスクで塞ぐ。

## 6. 順番1b の記録に入れるもの（封印係への申し送り）

`docs/stats/seal-order1.md` 3章 (3) の関門に従う。この文書から決まるものは次のとおり。
- 候補の一覧と基準の案のファイル：`docs/stats/counting.md`（この文書）と `src/stats/counting.py`。どちらも sha256 を記録に入れる（関門の2・4・6）。
- 候補の数と識別子：6つ、`C1`〜`C6`。基準の案の数と識別子：5つ、`B1`〜`B5`。代わりの順：3章 (1) の表。
- 正式な基準：`counting.OFFICIAL_CRITERION` の値（オーナーの決定のあと書き入れる）。`counting.official_criterion_status()` が `"decided"` であること。`"undecided"` なら封印しない。
- 規則のコード：`src/stats/counting.py` の sha256（関門の4。コードで書いた規則。入力の手順と行き先の `decide()` も含む）。順番2で、封印係はこの sha256 と一致するコードを自分で実行して当てはめる。
- 出力：`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B src/stats/counting.py` を引数なしで実行した標準出力のバイト列の sha256 も記録に入れることを提案する（定義の機械可読の写し）。

オーナーの決定（正式な基準、候補の一覧の承認）を書き入れると、`counting.py` と、この文書の sha256 は変わる。順番1b の封印は、書き入れたあとの版で行う。

## 7. 限界

- 候補は、収集係の今の集計の形（形式の版 2）から計算できるものだけである。形式の版が変わると `parse_day()` は止まり、4章 (2) で止まる。
- 3日は 2015年3月の初めで、手法を作る期間（約6年）のうちの3日だけである。B1・B2 の欄の選び方は、その3日の性質を表すだけで、のちのデータ源の仕様の変化（欄の付け方が変わるなど）は反映しない。
- 4章 (4) の穴（試しの run の最初のコミットと時刻証明より前の差し替え）。
- 待った回数は、封印係が順番2の試みを記録しなければ、第三者には分からない（4章 (2)）。
- (ア) で比率が変わらないのは、増えた収集元の話題の割合が前と同じ場合だけである（冒頭の A）。
- B1 と B2 のどちらがよいかは、データを見ずには決められない（3章 (3) の2）。どちらの分母でも、CLAUDE.md の目的の句の後半は、割り算では半分しか果たせない（冒頭の A）。
- B1・B2 の値（S の行）は、翻訳の組と `X` を含む（3章 (1)）。
- 仮定A はデータで確かめられない（3章 (3) の3）。
- 「検討した案をすべて」載せたかは、記録からは確かめられない（`seal-order1.md` 3章 (3) の4の限界）。統計係は、検討した案を3章の表と 3章 (4) にすべて書いた。
- B4 の 11/10 と B5 の 21/20 には、データからの根拠が無い。
