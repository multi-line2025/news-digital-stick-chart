# 報道量の数え方の候補と、候補から一つを選ぶ基準（T-028。順番1b で封印する提案）

仮の名前：counting-v1。正式な版の番号ではない。

## オーナーに承認をお願いすること

数え方とは、タグ（テーマ）の1日の報道量 r(d) を「何を何で割るか」の決め方です。オーナーの以前の決定で、数え方は試運転のあとに決めます。ただし、試運転のデータを見てから自由に選ぶと、都合のよい数え方を選べてしまいます。そこで、次の三つを試運転より前（method-access より前）に封印します（順番1b。`docs/stats/tags-naive.md` 0章の B）。

1. **数え方の候補の一覧（6つ。2章の表）**：分子は「そのテーマが付いた記事の数（V1 の欄）」「そのテーマが付いた記事の数（V2 の欄）」「そのテーマが記事の中で言及された回数（V2 の欄）」の3通り。分母は「全体の記事の数」か「全体の、分子と同じ数え方の合計」の2通り。3 × 2 で6つです。翻訳の記事は、どの候補でも数えません（オーナーの決定、案a）。どの候補も、収集係の日の集計の欄から計算できることを、テストで確かめました。
   - 確かめてほしい点：分母「分子と同じ数え方の合計」（C2・C4・C6）は、「記事の数」ではなく「テーマが付いた量の全体」です。CLAUDE.md の「同じ時間帯の全体の報道量で割った比率」に、この分母も当たると読んでよいか。当たらないと判断された場合は、C2・C4・C6 を外し、おすすめの B1 も使えなくなります（その場合のおすすめは B2）。
2. **基準の案の一覧（5つ。3章の表。採らなかった案も含めて封印・公開します）**：
   - B1：二つのテーマの欄（V1 と V2）のうち、テーマが一つも付かない記事が少ない方の欄を使う。記事の数で数え、分母は同じ数え方の合計。
   - B2：欄の選び方は B1 と同じ。分母は全体の記事の数。
   - B3：データを見ずに C1（V1 の記事の数 ÷ 全体の記事の数）に決め打ちする。
   - B4：1記事あたりのテーマの数が3日のあいだで1割を超えて揺れれば、分母を同じ数え方の合計にする。揺れなければ全体の記事の数。
   - B5：V2 の言及の回数が記事の数より5%を超えて多ければ、言及の回数で数える。多くなければ記事の数。
   - どの案も、試しの run の3日分（2015-03-02・03・04）の集計だけを入力にし、タグの一覧の件数や中身は見ません。入力・出力・同点のとき・該当なしのときを決めた規則で、`src/stats/counting.py` のコードとしても書きました。
3. **正式に使う基準を一つ**：統計係のおすすめは **B1** です。理由は3章 (3)。正式な結果（採点の対象）はこの一つだけで、ほかの基準の案と候補の結果は「比べるための参考で、正式ではない」として並べて公開します。
4. **基準の入力の決め方（4章）**：試しの run を何度か行った場合でも、使うのは、コミットした試しの run のマニフェストで最初に始まった run だけです。その run が3日分そろって終わっていなければ、ほかの run に代えず、順番2を止めます。

承認していただいたあと、正式な基準をコード（`OFFICIAL_CRITERION`）とこの文書に書き入れる作業は、別のタスクで行います。それまでは「未決（undecided）」で、未決のままでは封印しません。

## 1. 前提

- r(d) の分子と分母の数え方は、収集係の日の集計（`src/collector/gkg.py` 6章。`serialize_day` が書く。頭の行は `# gkg-day 2 <日> <mode>`）から計算できるものに限る（`docs/stats/seal-order1.md` 3章 (3) の監査の申し送り）。行単位の GKG は保存されないので、集計に無い量は、どの候補にも使えない。
- 集計の中で、候補と基準が読む行は次の5種類だけ（`gkg.py` の `serialize_day` と `add_line` を読んで確かめた）。
  - `V id theme`：その日に出たテーマの名前と、その日の中だけの番号。
  - `D g docs`：組 g の文書の数。行の時刻が区画の中で、欄の数と ID の形が合う行だけを数える。テーマが一つも付かない文書も含む。
  - `T g theme_id v1_docs v2_docs v2_mentions`：組 g とテーマの、V1THEMES にそのテーマがある文書の数、V2ENHANCEDTHEMES にある文書の数、V2ENHANCEDTHEMES での言及の回数（同じ文書で複数回なら回数分）。
  - `S name value`：行の件数の内訳。`docs_without_v1_theme`（V1THEMES にテーマが一つも無い文書の数）と `docs_without_v2_theme`（V2 も同じ）。**S の行は組ごとに分かれていない**（すべての組の合計）。
  - 頭の行：形式の版と、日と、mode（trial・official）。
- 組 g は、V2SOURCECOLLECTIONIDENTIFIER の値（1〜2桁の数字。形が違えば `X`）に、翻訳の印があれば `T` を付けたもの（`gkg.py` 4章）。
- **翻訳の記事は数えない**（オーナーの決定、案a。reviews/T-016.md「翻訳の記事については案aで良いです」）。どの候補も、最後の文字が `T` の組（`1T`、`XT` など）を、分子にも分母にも入れない。形の違う `X` は数える（ID と欄の数は合っていて、文書として数えられたものなので）。
- 組の番号の意味（どの番号がどの種類の収集元か）で組を絞る候補は作らない。番号の意味をこのプロジェクトの文書に記録しておらず、統計係の記憶で決めることになるため。
- 件数はすべて0以上の整数になる（`tagrules.build_tag_list()` の入力の条件。`tags-naive.md` 1章 (2)）。

### (1) 候補に入れなかった数え方（集計の形から計算できないもの）
- **テーマが一つでも付いた記事の数を分母にする**：組ごとの値が集計に無い（S の `docs_without_v1_theme` は、翻訳の組も含むすべての組の合計）。翻訳の組を除いて計算できないので入れない。
- **V1 の言及の回数**：収集係は V1THEMES を文書ごとに重なりを除いた集合として数えている（`add_line` の `s1`）。V1 の言及の回数は集計に無い。
- **同じ記事の重なり（転載・同じ URL）をまとめる数え方**：記事の URL と媒体の名前は、ディスクに書く前に捨てている（`gkg.py` 4章）。集計からはまとめられない。行の時刻がファイルの時刻と違う行（`rows_id_time_differs`）も、組ごとに分けて除けない。
- **翻訳の記事を数える数え方**：オーナーの決定（案a）で使わない。

## 3. 候補から一つを選ぶ基準の案

### (1) 共通の決まり
- **入力**：試しの run の3日分の日の集計（2015-03-02、2015-03-03、2015-03-04。`gkg.TRIAL_DAYS` と同じ）。どの run の集計にするかは4章の規則で一つに決まる。3日がこの順にそろっていなければ止まる（`CountingError`）。
- **出力**：候補の識別子ちょうど一つか、該当なし。**該当なしなら、順番2を封印しない**（ほかの候補やほかの基準に代えない）。止まったあとの扱いは `docs/stats/seal-order1.md` 3章 (2)。
- **使えるかの確かめ（usable）**：選んだ候補が、3日のどの日でも、分母 > 0 かつ分子の和 > 0 であること。満たさなければ該当なし。
- 比べるのは分数（`fractions.Fraction`）で、丸めは入れない。
- どの案も、引数は3日分の集計だけで、タグの一覧（件数も中身も）を受け取らない（`test_criteria_do_not_take_tag_list`）。
- 当てはめのコードは `counting.apply_all()`。すべての案を当てはめ、正式な基準の結果に `official: true` を付ける。

### (2) 各案の考え方（平易な説明）
- **B1・B2**：V1 と V2 は、どちらも記事に付いたテーマの欄で、どちらからも記事の数を数えられる。どちらを使うべきかを、データを見ずに決める根拠を統計係は持っていない。試しの run で分かる性質のうち、「テーマが一つも付かない記事がどれだけあるか」は、その欄が記事をどれだけ取りこぼすかを表す。取りこぼしの少ない欄を使う。
- **B3**：データを見ずに、最も素直な読み（ある話題の記事の数を、全体の記事の数で割る）に決める。試運転のデータは、計算できるかの確かめにだけ使う。
- **B4**：全体の記事の数で割る場合、1記事あたりに付くテーマの数が変わると、どのテーマの比率も一緒に動く。3日のあいだでもその揺れが大きければ、テーマの付いた量の全体で割る方が、その揺れを除ける。
- **B5**：言及の回数が記事の数とほとんど同じなら、言及の回数で数える意味は小さいので記事の数にする。はっきり多ければ、話題の扱いの大きさを表す言及の回数を使う。

### (3) 統計係のおすすめ：B1（理由を前提 → 結論で書く）
1. 単位（記事の数か、言及の回数か）
   - 前提1：`tags-naive.md` 1章 (2) の K = 10 の根拠（1週間で70件を超える報道を島とみなす根拠）は、記事の数で数える場合の話で、言及の回数で数えると弱くなる、と書いてある。
   - 前提2：K は順番1で封印し、変えない。
   - 結論：単位は記事の数にする（C1〜C4 の中から選ぶ）。B5 は言及の回数（C6）を選びうるので、おすすめにしない。
2. 分母（全体の記事の数か、同じ数え方の合計か）
   - 前提3：CLAUDE.md は、比率にする理由を「収集元のサイト数の増減や、テーマ付与の変化による見かけの変動を除くため」と書いている。
   - 前提4：収集元が増えて記事が増えると、全体の記事の数も、テーマの付いた量の全体も増える。テーマの付け方が変わって、どの記事にもテーマが多く付くようになると、テーマの付いた量の全体は増えるが、全体の記事の数は増えない。
   - 結論：前提3の二つの理由の両方に当たるのは、同じ数え方の合計で割る分母（C2・C4）である。全体の記事の数（C1・C3）は、一つ目の理由にしか当たらない。B2・B3 は全体の記事の数で割るので、おすすめにしない。
   - 但し書き：テーマの付け方の変化が、すべてのテーマに同じ割合で起きる場合にだけ、きれいに除ける。一部のテーマにだけ起きた変化は、どちらの分母でも除けない。大きな出来事で特定のテーマが急に増えると、テーマの付いた量の全体が増えて、ほかのテーマの比率が少し下がる。これは全体の記事の数で割る場合にも、記事の数が増えれば同じく起きる。
   - この結論は、分母「同じ数え方の合計」が CLAUDE.md の「全体の報道量」に当たるという読みに依る。オーナーに確かめてほしい（冒頭の1）。
3. 欄（V1 か V2 か）
   - 前提5：V1 と V2 のどちらがよいかを、データを見ずに決める根拠を統計係は持っていない（記憶にあるデータ源の説明に頼ることになる）。
   - 前提6：「テーマが一つも付かない記事の数」は、試しの run の3日で分かるデータ源の性質で、タグの一覧の件数や中身に依らない。
   - 結論：欄は、テーマの付かない記事が少ない方を選ぶ（B1）。
4. 3日の揺れで決める案（B4）
   - 前提7：3日のデータで分かる揺れは、手法を作る期間（約6年）の揺れをほとんど表さない。区切りの 11/10 にもデータからの根拠が無い。
   - 結論：B4 はおすすめにしない。分母は 2 の理由で決める。
5. 以上の 1・2・3 から、おすすめは B1（出力は C2 か C4）。

### (4) 基準の案に入れなかった考え
次の考えは検討したが、条件（入力・出力・同点・該当なしが決まり、タグの一覧の件数や中身を見ずに当てはめられる規則であること）に合わないか、試しの run の3日分からは計算できないので、基準の案に入れなかった。
- 候補ごとに作ったタグの一覧の件数が、ある範囲に入る候補を選ぶ：タグの一覧の件数を見るので、条件に合わない。
- 候補ごとの N_med や A の大きさで選ぶ：N_med は手法を作る期間の全体の値で、3日分の入力からは計算できない。3日分の値で代えると、件数に近い量を見て選ぶことになる。
- 比率の日ごとの安定さ（長い期間の分散など）で選ぶ：3日では計算の意味が無い。
- 予言の当たりやすさで選ぶ：手法を作る期間の全体のデータが要り、試運転の段階では計算できない。結果を見て数え方を選ぶことにもなる。

## 4. 基準の入力を一つに決める規則（T-025 の監査の中2）

試しの run は、コードを変えると run_id が変わり、別の run としてもう一度行える（`gkg.py` 5.1章）。結果を見てから、どの run の集計を入力にするかを選べないように、入力を次の規則で一つに決める。規則のコードは `counting.select_trial_input()` と `counting.check_prefix_versions()`。

1. **読むマニフェスト**：順番2を封印する commit（HEAD、40桁）の `data/manifest/gdelt-gkg-trial.jsonl`（`git show <HEAD>:data/manifest/gdelt-gkg-trial.jsonl` の標準出力のバイト列）。作業ツリーのファイルが、このバイト列と同じであること。
2. **追記だけであること**：`git log --all --full-history --format=%H -- data/manifest/gdelt-gkg-trial.jsonl` の各 commit の版（ファイルが無い版は空）が、どれも 1 のバイト列の先頭と同じであること（並び順は使わない）。合わなければ止まる。
3. **使う run**：1 のマニフェストで、行の並びで最初の `kind` が `run-start` の行の `run_id`（R）。その行の `mode` が `trial`、`trial` が `true` であること。**R のほかの run は使わない。** R が終わっていない、日がそろっていない、などのときも、ほかの run に代えずに止まる。
4. **R の終わりと日**：R の `run-complete` の行があること。R の `day` の行が、3日（2015-03-02・03・04）の各日にちょうど一つずつあり、ほかの日が無いこと。各行の `mode` が `trial`、`file_name` が `gkg-trial-<R>-day-<YYYYMMDD>.tsv.gz`、`sha256` が16進64字であること。
5. **正式な run との照合**：順番2の時点で、正式な run のマニフェスト（`data/manifest/gdelt-gkg-method.jsonl`）に `run-start` があれば、その `trial_run_ids` の最初の要素が R であること。違えば止まる。
6. **ファイルの照合**：各日の日の集計のファイル（外付けディスクの試しの run の保存先にある）のバイト列の sha256 が、4 の `day` の行の `sha256` と一致すること。頭の行の日と mode が、その日と `trial` であること。一つでも違えば止まる（`apply_to_inputs()`）。
7. どれか一つでも満たさなければ、順番2を封印しない（`docs/stats/seal-order1.md` 3章 (2)）。

「最初の run」にした理由（前提 → 結論）：
- 前提1：最初の run-start の行は、コミットしたあとは、履歴を書き換えないかぎり変えられない（2 で確かめる）。
- 前提2：最後の run にすると、集計を見たあとでコードを変えて新しい試しの run を行えば、入力を差し替えられる。
- 前提3：最初の run が途中で止まった場合も、同じコードなら同じ run_id で再開して終えられる（`gkg.py` 5章）。
- 結論：最初の run を使い、終わっていなければ待つか止まる。最後の run や「終わった run のうち最初のもの」は、前提2 の差し替えの余地を残すので採らない。

`counting.py apply <マニフェスト> <日の集計のフォルダ>` は 3・4・6 を行い、すべての基準の案の結果を出力する。1・2・5 は git と正式な run のマニフェストを読むので、封印係が自分のコードで行う。

## 5. 順番に矛盾が無いことの確かめ

順番は `tags-naive.md` 5章の表と `seal-order1.md` による。

| 段 | 何をするか | 何を読むか |
|---|---|---|
| 順番1 | 除外の規則と入れる規則を封印 | データを読まない |
| 順番1b | 候補の一覧（2章）、基準の案（3章）、正式な基準を封印（このタスクの提案に、オーナーの承認を得たもの） | データを読まない（`counting.py` はデータ無しで定義を出す） |
| method-access | 手法を作る期間のデータへの最初の接触の記録 | — |
| 試しの run | 3日分の集計を作る。入口のスクリプトは、除外の規則の封印と method-access の記録を求める（`src/collector/acquire_gkg.py`） | GKG（3日分） |
| 順番2 | 4章の規則で入力を決め、正式な基準を当てはめ、選ばれた候補を封印 | 試しの run の集計（3日分）だけ |
| 順番3〜5 | 数え方とのつながり、欠けた日の一覧、タグの一覧の結果（6つの候補すべて） | 正式な run の集計 |

- 順番1b の封印は、基準の中身（入力の種類、計算、同点、該当なし）だけを決め、データの値を使わない。値を使うのは順番2で、そのときには基準が封印されている。よって「基準を method-access より前に封印し、当てはめを試しの run のあとに行う」順に矛盾は無い。
- 順番2の結果は、封印した基準と、4章で一つに決まる入力だけで決まる。順番2をいつ行うか（正式な run の前か後か）で結果は変わらない。
- 試しの run の集計は、正式な run の結果としては使わない（`gkg.py` 5.1章）。順番2で基準の入力に使うのは、数え方を選ぶためで、タグの一覧や判定には使わない。
- 統計係が確かめた範囲では、矛盾は無かった。

## 6. 順番1b の記録に入れるもの（封印係への申し送り）

`docs/stats/seal-order1.md` 3章 (3) の関門に従う。この文書から決まるものは次のとおり。
- 候補の一覧と基準の案のファイル：`docs/stats/counting.md`（この文書）と `src/stats/counting.py`。どちらも sha256 を記録に入れる（関門の2・4・6）。
- 候補の数と識別子：6つ、`C1`〜`C6`。基準の案の数と識別子：5つ、`B1`〜`B5`。
- 正式な基準：`counting.OFFICIAL_CRITERION` の値（オーナーの決定のあと書き入れる）。`counting.official_criterion_status()` が `"decided"` であること。`"undecided"` なら封印しない。
- 規則のコード：`src/stats/counting.py` の sha256（関門の4。コードで書いた規則）。順番2で、封印係はこの sha256 と一致するコードを自分で実行して当てはめ直す。
- 出力：`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B src/stats/counting.py` を引数なしで実行した標準出力のバイト列の sha256 も記録に入れることを提案する（定義の機械可読の写し）。

オーナーの決定（正式な基準、候補の一覧の承認）を書き入れると、`counting.py` と、この文書の sha256 は変わる。順番1b の封印は、書き入れたあとの版で行う。

## 7. 限界

- 候補は、収集係の今の集計の形（形式の版 2）から計算できるものだけである。形式の版が変わると `parse_day()` は止まる。その場合は新しい版として扱う。
- 試しの run の3日は 2015年3月の初めで、手法を作る期間（約6年）のうちの3日だけである。B1 の欄の選び方は、その3日の性質を表すだけで、のちのデータ源の仕様の変化（欄の付け方が変わるなど）は反映しない。
- 試しの run のマニフェストは、試しの run が終わったあとにコミットする（`gkg.py` 5.1章）。最初のコミットより前に、試しの run のファイルを保存先の外へ移し、マニフェストの行も消して、コードを変えた別の試しの run を行えば、4章の「最初の run」を差し替えられる。これは `gkg.py` 5.1章の限界と同じで、統計係の範囲では塞げない。試しの run の run_id はコードの sha256 から決まるので、コードを変えたことは、正式な run の run_id や run-start の `trial_run_ids` と比べて分かる場合がある。
- B1・B2 の値（S の行）は、翻訳の組と `X` を含む（3章 (1)）。
- 「検討した案をすべて」載せたかは、記録からは確かめられない（`seal-order1.md` 3章 (3) の4の限界）。統計係は、検討した案を3章の表と 3章 (4) にすべて書いた。
- B4 の 11/10 と B5 の 21/20 には、データからの根拠が無い。
