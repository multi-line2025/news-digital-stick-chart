### (3) 二つの分母の違い（(2) の問いの説明。記録として残す）
例：ある日の記事が1000本、「天気」のテーマが付いた記事が10本、テーマの合計が5000とする。記事の数で割ると 10 ÷ 1000 = 1%、テーマの合計で割ると 10 ÷ 5000 = 0.2%。データ源の側で次の変化が起きたとき、天気の比率は次のように動く（例の数は手で計算したもの。`tests/stats/test_counting.py` の `TestDenominatorChanges` は、作り物のデータで、上がる・下がる・変わらないの向きだけを確かめた）。

| データ源の側の変化 | 記事の数で割る | テーマの合計で割る（C7 も同じ） |
|---|---|---|
| (ア) 収集元が倍に増える（記事2000本、天気20本、合計10000） | 1%。変わらない | 0.2%。変わらない |
| (イ) どの話題も一律に付けやすくなる（記事1000本のまま、天気15本、合計7500） | 1.5%。**上がる** | 0.2%。変わらない |
| (ウ) 新しい話題「X」を付け始め、500本に付いた（記事1000本、天気10本、合計5500） | 1%。変わらない | 約0.18%。**下がる** |

- (ア) で変わらないのは、増えた収集元の話題の割合が前と同じ場合だけである。違う話題の多い収集元が加われば、どちらの分母でも比率は動く。
- (ウ) の逆に、データ源がある話題を付けるのをやめると、テーマの合計で割った場合は、ほかのすべてのタグの比率が上がる。どちらの分母でも、付け始めた・やめた話題そのものの比率は動く。
- 表で「上がる」「下がる」となった場合、関係のないすべてのタグが同じ割合で一緒に動く。島の判定は「普段の水準の何倍か」で決まるので、一緒に動く割合が大きいほど、閾値の近くにあったタグが閾値を越えたり（見かけの島）、越えなくなったり（島の見落とし）する。割合が小さければ影響は小さいが、ゼロではない。GDELT で (イ) と (ウ) がどれくらいの大きさで起きるかは、データを見ないと分からない。
- **CLAUDE.md の目的の句との関係**：比率にする目的は「収集元のサイト数の増減や、テーマ付与の変化による見かけの変動を除くため」である。前半（収集元の増減）は (ア) で、どちらの分母でも除ける。後半の「テーマ付与の変化」には (イ) と (ウ) の両方が入る。記事の数で割ると、(ウ) では関係のないタグを動かさないが、(イ) ではすべてのタグが一緒に動く。テーマの合計で割ると、(イ) は打ち消すが、(ウ) で関係のないタグが一緒に動く。**どちらの分母でも、割り算で果たせるのは後半の目的の半分だけである。**
- **割り算以外のしくみでも、残りの半分は除けない**（T-028 の監査の軽-1 で直した）。普段の水準を直近365日の7日平均の中央値でとる場合（普段の水準の数え方は未決事項2で確定する）、データ源の側の段差は、段差のあとの日が365日の半分を超えるまで（約半年）中央値に取り込まれず、それまでは比率の段差がそのまま残る。取り込まれたあとも、段差の前後をまたぐ比べ方には残る。消えたテーマに印を付けることは、そのテーマの扱いを決めるだけで、ほかのタグの比率の動きを除かない。
- C7 は、テーマの合計で割る側にあたる。そのため (イ) は打ち消し、(ウ) では関係のないタグが一緒に動く。加えて C7 は、同じ記事で V1 と V2 の両方に付いても1回と数えるので、データ源が V1 から V2 へ移る（片方の欄だけに付くようになる）変化では、そのテーマの数が変わらない（`test_c7_counts_once_when_both`）。V1 と V2 の数を単純に足す数え方では、移行が減少に見える。

- **B1・B2**：V1 と V2 は、どちらも記事に付いたテーマの欄で、どちらからも記事の数を数えられる。どちらを使うかを、3日分で分かる「テーマが一つも付かない記事の数」で決める。この決め方は、下の (3) の仮定A を置いたときに意味を持つ。B1 と B2 の違いは分母だけである（0章 (3)）。C7 は、欄を選ばずに両方を使う。

### (3) 案の性質（前提 → 結論。正式な数え方を選ぶためのものではなく、参考の結果を読むための説明）
1. 単位（記事の数か、言及の回数か）
   - 前提1：`tags-naive.md` 1章 (2) の K = 10 の根拠（7日で70件を超える報道を島とみなす根拠）は、記事の数で数える場合の話で、言及の回数で数えると弱くなる、と書いてある。
   - 前提2：K は順番1で封印し、変えない。
   - 結論：B1・B2 は記事の数で数える（C1〜C4 から選ぶ）。B5 は言及の回数（C6）を選びうるので、K の根拠が弱くなる場合がある。
2. 分母（記事の数か、テーマの合計か）
   - 前提3（0章 (3) の表。`TestDenominatorChanges` で向きを確かめた）：記事の数で割ると、(ア) を打ち消し、(ウ) では関係のないタグを動かさないが、(イ) ではすべてのタグが一緒に動く。テーマの合計で割ると、(ア) と (イ) を打ち消すが、(ウ) で関係のないタグが一緒に動く。
   - 前提4：CLAUDE.md の目的の句の後半「テーマ付与の変化」には (イ) と (ウ) の両方が入る。
   - 前提5：GDELT で (イ) と (ウ) がどれくらいの大きさで起きるかは、データを見ないと分からない（統計係はデータを見ていない。記憶にあるデータ源の説明には頼らない）。
   - 結論：前提3・4 から、どちらの分母でも、割り算で果たせるのは後半の目的の半分である。前提5 から、どちらが優れているかはデータを見ずに言えない。正式な数え方の分母は、オーナーが「テーマの合計」に決めた（0章 (1)）。
3. 欄（V1 か V2 か。B1・B2 に共通）
   - 前提6：V1 と V2 のどちらがよいかを、データを見ずに決める根拠を統計係は持っていない（記憶にあるデータ源の説明に頼ることになる）。
   - 仮定A（データでは確かめられない）：テーマが一つも付かない記事の多くは、話題の無い記事ではなく、その欄が話題を付けそこねた記事である。
   - 前提7：「テーマが一つも付かない記事の数」は、3日分の集計で分かるデータ源の性質で、タグの一覧の件数や中身に依らない。
   - 結論：仮定A が成り立つなら、テーマの付かない記事が少ない欄の方が、話題の取りこぼしが少ない。B1・B2 は欄をそれで選ぶ。
   - 仮定A が成り立たない場合、比べているのは「どちらの欄が何かしらのテーマを多くの記事に付けるか」だけで、取りこぼしの少なさは言えない。その場合、欄の選び方に根拠は無く、決め打ちの B3（記事の数で割る）と B2 の間にも、どちらがよいかの根拠は無い。
4. 3日の揺れで決める案（B4）
   - 前提8：3日のデータで分かる揺れは、手法を作る期間（約6年）の揺れをほとんど表さない。区切りの 11/10 にもデータからの根拠が無い。
   - 結論：B4 の分母の選び方は、3日の偶然の揺れで決まりうる。

### (4) 基準の案に入れなかった考え
次の考えは検討したが、条件（入力・出力・同点・該当なしが決まり、タグの一覧の件数や中身を見ずに当てはめられる規則であること）に合わないか、3日分からは計算できないので、基準の案に入れなかった。
- 候補ごとに作ったタグの一覧の件数が、ある範囲に入る候補を選ぶ：タグの一覧の件数を見るので、条件に合わない。
- 候補ごとの N_med や A の大きさで選ぶ：N_med は手法を作る期間の全体の値で、3日分の入力からは計算できない。3日分の値で代えると、件数に近い量を見て選ぶことになる。
- 比率の日ごとの安定さ（長い期間の分散など）で選ぶ：3日では計算の意味が無い。
- 予言の当たりやすさで選ぶ：手法を作る期間の全体のデータが要り、試運転の段階では計算できない。結果を見て数え方を選ぶことにもなる。

## 4. 順番2の入力を一つに決める規則と、止まったあとの行き先

順番2では、試しの run の3日分（4章 (2) の場合だけ正式な run の同じ3日）を入力にして、(a) 正式な数え方 C7 がその入力で計算できるかを確かめ、(b) 参考の基準 B1〜B5 の結果と、(c) 欄の手厚さ（5章）を記録する。正式な数え方は順番1b で決まっているので、入力によって変わらない。試しの run は、コードを変えると run_id が変わり、別の run としてもう一度行える（`gkg.py` 5.1章）。結果を見てから、どの run の集計を入力にするかを選べないように、入力を次の規則で一つに決める。止まったあとの行き先も、ここで決めて順番1b で一緒に封印する。規則のコードは `counting.decide()`（中で `select_trial_input()`・`select_official_input()`・`apply_all()` を使う）と `counting.check_prefix_versions()`。

### (1) 読むもの
- 試しの run のマニフェスト `data/manifest/gdelt-gkg-trial.jsonl` と、正式な run のマニフェスト `data/manifest/gdelt-gkg-method.jsonl`。どちらも、順番2を封印する commit（HEAD、40桁）の版（`git show <HEAD>:<パス>` の標準出力のバイト列。ファイルが無ければ空）を読む。
- **git の確かめ**（封印係が自分のコードで行う）：作業ツリーのファイルが HEAD の版と同じこと。`git log --all --full-history --format=%H -- <パス>` の各 commit の版（ファイルが無い版は空）が、どれも HEAD の版の先頭と同じこと（追記だけ。並び順は使わない）。どちらかのマニフェストが通らなければ止まる（`decide()` に None を渡す）。

### (2) 手順と行き先（`decide()`。T-028 差し戻し2回目 中-B1・中-B2 で直した）
R は、試しの run のマニフェストで行の並びで最初の `run-start` の `run_id`。ほかの試しの run は使わない。

| 順 | 確かめること | 満たさないとき |
|---|---|---|
| 1 | 二つのマニフェストが (1) の git の確かめに通る。JSON として読め、最初の `run-start` が決まった形（試しの run は `mode: trial`・`trial: true`・`official: false`、正式な run は `mode: official`・`trial: false`・`official: true`） | 止まる |

### (4) 「最初の run」にした理由と、残る穴
- 前提1：最初の run-start の行は、試しの run のマニフェストをコミットし、さらにそのコミットが履歴を書き換えられない形（時刻証明。OpenTimestamps など）になったあとは、変えられない。それより前は、コミットを作り直したり、コミットの前に行を消したりできる。
- 前提2：最後の run にすると、集計を見たあとでコードを変えて新しい試しの run を行えば、入力を差し替えられる。
- 前提3：最初の run が途中で止まった場合も、同じコードなら同じ run_id で再開して終えられる（`gkg.py` 5章）。
- 結論：最初の run を使う。最後の run や「終わった run のうち最初のもの」は、前提2 の差し替えの余地を残すので採らない。
- **順番2を行う時機**：(2) では、1段目か2段目か止まるかは、正式な run の開始のときの試しの run のマニフェストの中身（2 で確かめる）だけで決まる。1段目の記録とファイルがそろったあとは、いつ行っても1段目で決まり、ファイルを壊せば止まる。よって、順番2をいつ行うかで、使う段を選ぶことはできない。
- 残る穴（T-028 の監査の中2）：前提1 の「変えられなくなる」時点より前に、運営側は3日分の集計を見て B1〜B5 の結果を計算できる。気に入らなければ、マニフェストの行とファイルを消して（または移して）、別の run_id で取り直せる。正式な数え方は C7 に決め打ちなので、この穴で変わりうるのは参考の結果と、順番2の欄の手厚さだけである。試しの run を途中で止めて終わらせないまま正式な run を始める操作や、試しの run を二つ以上行う操作は、(2) で止まる（差し戻し3回目 中-3）。止まれば、そのことが公開される。残るのは、マニフェストの最初のコミットと時刻証明より前に、行とファイルを消して取り直す操作で、今の試しの run の作りでは、統計係の範囲で塞げない。試しの run を2段にするなど作りを変える収集係（と封印係）の別のタスクが要り、その合格を順番1b の封印の前提条件にする（`seal-order1.md` 3章 (3)）。
- 2段目の入力は、同じ3日の同じ GKG のファイルを、正式な run のコードで集計したものである（`gkg.py` 5.1章「正式な run は、試しの run の3日も含めて、全部の日を取り直す」）。試しの run と正式な run のコード（run_id）が同じで、取れなかったファイルが同じなら、中身は同じになる。違いうるのは、二つの run の間でコードを変えた場合と、取れなかったファイルが違う場合だけである。そのため、二つの run_id と、両方の run の3日の `failed_files` を出力と記録に入れ、公開物で並べて示す。

`counting.py apply <試しの run のマニフェスト> <正式な run のマニフェスト> <試しの run の保存先> <正式な run の保存先>` は、(2) を行い、C7 が使えるかの確かめ、すべての参考の基準の案の結果、欄の手厚さを出力する（終了コード：決まった 0、止まった 1、待つ 3）。(1) の git の確かめは封印係が行う。通らないマニフェストは `FAILED`、HEAD にファイルが無いマニフェストは `EMPTY` と書いて渡す。それ以外で読めないパス（ファイルが無いなど）は、git の確かめに通らないものと同じに扱い、止まる（T-028 の監査の軽-4）。

## 8. 限界

- 候補は、収集係の今の集計の形（形式の版 3）から計算できるものだけである。形式の版が変わると `parse_day()` は止まる。
