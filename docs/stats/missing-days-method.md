# 順番4：手法を作る期間の区画の、欠けた日の一覧（T-087、T-089 で作り直し）

文書の版：`missing-days-method-v3`

この文書は、手法を作る期間の区画（2015-03-02〜2020-12-14）について、欠けた日の一覧をどう作るかを定める。
一覧を作るコードは `src/stats/missing_days.py`、テストは `tests/stats/test_missing_days.py`。
封印は封印係が行う。統計係はこの文書とコードを作るだけで、封印しない。

## 1. 規則

規則は docs/stats/candidates.md 3章 (5)（seq 2 で封印済み）のとおりで、この文書では変えない。要点を引く。

- 日の区切りは、収集係の規則（15分ファイルの時刻と UTC の暦日の対応。src/collector/filelist.py）に従う。
- 「取得できたファイル」は、ファイル一覧に載り、取得の記録で取得とハッシュの照合に成功した15分ファイル。
- 次のどちらかに当たる日を欠けた日とする（`candidates.day_is_missing()`）。
  - 取得できたファイルが96本のうち72本未満
  - 取得できたファイルから数えた全体の報道量が0
- 一部が欠けた日（72本以上96本未満）は欠けた日としない。

コードは、判定に `candidates.day_is_missing(present_slots, total_volume)` をそのまま呼ぶ。72・96 の値も candidates.py の定数（`MIN_PRESENT_SLOTS`・`SLOTS_PER_DAY`）から取る。

## 2. 規則の二つの量を、何で数えるか

| 規則の量 | 数えるもの |
|---|---|
| 取得できたファイルの数（present_slots） | マニフェストの day の行の `files_ok` |
| 取得できたファイルから数えた全体の報道量（total_volume） | その日の日の集計から数えた、正式な数え方 **C7 の分母** |

### (1) `files_ok`
- 収集係の取得のコード（src/collector/gkg.py）が、その日のファイル一覧に載ったファイルのうち、取得・ハッシュの照合・**集計**のすべてに成功したものを数えた値である（T-087 の監査 軽-1）。
  - 取得とハッシュの照合に成功しても、集計に失敗したファイルは入らない。そのため、candidates.md の「取得できたファイル」より少し狭い。手法を作る期間の正式な run では、この差にあたるファイルは無かった（T-087 の監査）。
- **ファイルの数であって、15分の枠の数ではない。** 1日の96の枠のうちいくつが埋まったかを数えた値ではない。candidates.md の「96本のうち72本」は、この本数で当てはめる。

### (2) 全体の報道量 = C7 の分母
- **読み方**：candidates.md 168行の「取得できたファイルから数えた全体の報道量」は、その日の取得できたファイルから数えた、正式な数え方 C7 の分母と読む（reviews/T-087.md 3章のリードの判断の訂正）。
  - C7 の分母は、V1 か V2 の少なくとも一方にテーマが付いた文書の数を、数える組（翻訳の印の無い組）とすべてのテーマで足したものである（docs/stats/counting.md、順番1b で封印）。
- **数え方**：順番1b（seq 6）で封印した `src/stats/counting.py` の関数をそのまま使い、新しく書かない。
  - `counting.candidate_counts(counting.parse_day(日の集計), counting.OFFICIAL_CANDIDATE)` の2つ目の値。
  - コードは、使う counting.py の sha256 が、順番1b の記録の値（`6f25985b…8c9fd3`）と同じであることを確かめてから動く（下の (3)）。
- **T-085 の読み方（docs）を取り消した理由**（reviews/T-087.md 3章から引く）：
  - T-085 では、「CLAUDE.md は報道量を記事の数として扱っている」を理由に、マニフェストの `docs`（取得できたファイルの文書の数）と読んだ。
  - しかし CLAUDE.md 21〜22行は、報道量を「全体の報道量で割った比率」で扱い、正式な数え方の分母を「同じ数え方の全テーマの合計」と定めている。candidates.md 102行も、「全体の報道量」を r(d) の分母の意味で使っている。tags-naive.md 74・138行、counting.md 259行も同じ使い方である（T-087 の監査 中-2）。
  - 前提：CLAUDE.md と封印済みの文書が、「全体の報道量」を比率の分母の意味で使っている。結論：168行の「全体の報道量」も、正式な数え方 C7 の分母と読む。168行だけを docs と読むと、同じ語が二つの量を指すことになる。
  - 読み方の訂正は、日の集計を開く前（reviews/T-087.md の記録の時点）に確定した。そのとき、C7 の分母が0の日があるかは、誰にも分かっていなかった。
- **counting.md 259行の分岐**：counting.md 259行は「順番5で、欠けた日でない日の C7 の分母が 0 のときは止める」と定めている。この読み方では、C7 の分母が0の日は、この順番4で必ず欠けた日になる。したがって、259行の分岐は起こりえないものになる。止める側の分岐が余るだけで、害は無い（reviews/T-087.md 3章）。counting.md の文言は変えない。

candidates.md と counting.md の文言は変えない。この文書は読み方を足すだけである。

### (3) 中で使うコードの照合（T-093）
`missing_days.py` が中で使う3つのファイルは、封印の記録が縛る sha256 と同じでなければ、何も読まずに止まる。照らす値と出どころは次のとおり（記録を読んで決めた。コードの `SEALED_CODE`）。

| ファイル | sha256 | 出どころ（記録の欄） |
|---|---|---|
| `src/stats/periods.py` | `81de229d065196a26e15d90c5a80eb1043ca534a6eaf66cdebd36285ae087605` | seq 1（kind `periods`）の `targets` の role `code`。seq 2（kind `candidates`）の `targets` の role `import` も同じ値 |
| `src/stats/candidates.py` | `21b5838782991596057be2fdffdeac596bf4548517ef077e5c4547a719512e89` | seq 2（kind `candidates`）の `targets` の role `code` |
| `src/stats/counting.py` | `6f25985b21cd8ac93680b81308f3d1860b4ae6496577e10141d1e17ecf8c9fd3` | seq 6（kind `stats-order1b`）の中身（`sealed/stats-order1b-44a7cdfc….json`）の `files` |

照らし方は二段である。
1. 3つのファイルは、import の仕組みを通さずに読み込む（`_load_verified()`。T-096）。ファイルを1回だけ読み、そのバイト列の sha256 を記録し、同じバイト列を compile して実行する。そのため、`__pycache__` に古い `.pyc` があっても読まない（`-B` は `.pyc` を書かないだけで、読むことは止めない）。candidates.py の `import periods` も、この方法で読み込んだ periods を使う。
   - 実行のはじめに、読み込んだモジュールが `src/stats` のそのファイルから作ったものであることと、動いているコードのバイト列の sha256 が表の値と同じことを確かめる（`check_stats_code()`）。合わなければ、マニフェストも日の集計も読まずに止まる。
2. gkg-run-result の関門を通ったあとで、関門が検証した封印の記録を読み、表の値が上の欄の値と同じことを確かめる（`check_sealed_code_in_ledger()`）。seq と kind が表と合わない場合も止まる。この確かめは、日の集計を開く前に行う。

テスト：`test_code_sha_checked`・`test_module_path_checked`・`test_pins_match_real_ledger`（本物の封印の記録で通り、値を一つ変えると止まる）。合成の run のテストでは、写しの順番1b が仮の中身なので、counting.py の照合で止まることを確かめる。そのあとは、seq 1・2 の照合だけを残して流す。

## 3. 入力

- **day の行**：`src/collector/gkg.py` の `official_day_records()` だけから取る。
  - この関数は、最初に封印係の関門 `ledger.require_gkg_run_result("official", run_id)` を呼ぶ。gkg-run-result の記録（seq 12。マニフェストの時刻証明）が無い・合わなければ、マニフェストを読まずに止まる。
  - 読むのは、gkg-run-result が封印したマニフェスト（`data/manifest/gdelt-gkg-method.jsonl`）の先頭だけである。
  - そのあとで、同じ関門をもう一度呼んで gkg-run-result の記録を受け取り、その seq・記録の行の sha256（`ledger.canonical_line` の sha256）と、記録の中身にある使ったマニフェストの先頭の行数と sha256 を、出力の `input` に入れる（T-093）。関門の返した記録が封印の記録の中に同じ形であること、中身の mode と run_id がこの run と同じことを確かめる。
- **日の集計**：day の行の `file_name` のファイルだけを、引数 `--store` で渡した置き場所から開く。
  - 本物の置き場所は `/Volumes/LACIE SHARE/news-stick-data/gkg-method`。
  - 開いたバイト列の sha256 を、day の行の `sha256` と照らす。合わなければ（ファイルが無い場合も）、一覧を作らずに止まる。
  - 日の集計の頭の行の日と mode が、day の行と合わなければ `counting.parse_day()` が止まる。
  - day の行の検査（下）がすべて通るまで、日の集計は1つも開かない。
  - 欠けた日も含め、区画のすべての日の日の集計を開いて、C7 の分母を数える。
- **日の集計から数えるのは、各日の C7 の分母だけ**。テーマごとの数・比率・判定・上位のテーマなど、ほかの量は出力しない。`candidate_counts()` が中で作るテーマごとの数は、その場で捨てる。
- 取得の記録（fetch log）は読まない。ネットワークは使わない。ファイルを書かない（標準出力だけ。開いた数と所要時間を標準エラーに出す）。

**day の行の検査（合わなければ、日の集計を開かずに止まる）**：
- 区画の各日に、正式な run（mode が official）の day の行がちょうど1つある。行の無い日、区画の外の行、同じ日の二つの行があれば止まる。行の無い日を推測で埋めることはしない。
- run_id が1つだけ。
- `files_ok`・`files_listed` が0以上の整数で、`files_ok` ≤ `files_listed`、`files_ok` ≤ 96。
- `file_name` が決まった名前（`counting.day_file_name("official", run_id, 日)`）と同じ。`sha256` が64桁の16進。
- 区画の端は `periods.FROZEN_BLOCKS` の method の区画と、`gkg.DATA_START`・`gkg.METHOD_BLOCK_END` の両方と一致する。

## 4. 出力の形

コマンド（プロジェクトのルートで）：

```
STORE="/Volumes/LACIE SHARE/news-stick-data/gkg-method"
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B src/stats/missing_days.py --store "$STORE"            # 一覧の JSON
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B src/stats/missing_days.py --store "$STORE" --sha256   # その JSON の sha256
```

所要時間の目安：**60〜100分**。2115個の日の集計をすべて開いて `parse_day()` の検査を通すためで、ほとんどが計算の時間である。実測は、T-089 で約92分、T-089 の監査で約66分だった（機械と置き場所の状態で変わる）。

JSON は UTF-8、キーの順（`sort_keys`）、`indent=2`、末尾に改行1つ。sha256 は、この出力のバイト列全体の値である（`shasum -a 256` と同じ値）。置き場所のパスと実行の日時は出力に入れない（どこで流しても同じ値になるようにするため）。

| キー | 中身 |
|---|---|
| `label` | `missing-days-method-v3`（下の「label の扱い」） |
| `block` | 区画の名前と端（`method`、2015-03-02、2020-12-14） |
| `rule` | 規則の出典、使う関数、96・72、二つの量を何で数えたか、正式な候補（C7）、counting.py・candidates.py・periods.py の sha256 |
| `input` | 入口、run_id、day の行の数、開いた日の集計の数、sha256 を照らしたこと、gkg-run-result の記録の seq と記録の行の sha256（`gkg_run_result_seq`・`gkg_run_result_record_sha256`）、使ったマニフェストのパス・先頭の行数・sha256（`manifest_path`・`manifest_lines`・`manifest_sha256`） |
| `days_in_block` | 区画の日数 |
| `missing_count` | 欠けた日の数 |
| `missing_days` | 欠けた日の一覧（日付の順）。各日に `day`・`files_ok`・`files_listed`・`c7_denominator`・`below_min_files`（72本未満か）・`zero_c7_denominator`（C7 の分母が0か） |
| `zero_c7_denominator_days` | C7 の分母が0の日の一覧 |
| `c7_denominator_by_day` | 区画のすべての日の C7 の分母 |
| `partial_days_count` | 一部が欠けた日（72本以上96本未満で、分母が0でない日）の数 |

`files_listed` は、欠けの原因がファイル一覧の側か取得の側かを読み分けるために出す。規則の判定には使わない。

**label の扱い**（T-087 の監査 軽-4）：
- label は、この文書の版と1対1にする。コードの定数 `LABEL` と、この文書の冒頭の「文書の版」を同じにし、テスト（`test_label_matches_doc`）で照合する。
- 引数では変えられない。規則・読み方・入力・出力の形を変えるときは、文書の版とコードの `LABEL` を一緒に上げ、新しい版として封印する。
- v1 は T-087 の版（全体の報道量 = docs。封印していない）。v2 は T-089 の版（全体の報道量 = C7 の分母。封印していない）。v3 はこの版（T-093。規則と読み方は v2 と同じ。中で使うコードの照合を足し、出力の `rule` と `input` に欄を足した）。T-096 の直し（照合したバイト列から読み込む）は、規則・読み方・入力・出力の形を変えないので、版は v3 のままとする。
- 文書の中で今の版を書く箇所は、冒頭の「文書の版」、4章の表の `label` の行、この節の「はこの版」の3つである。テスト（`test_label_matches_doc`）が、3つとも `LABEL` と同じことを確かめる。
- 正式な回の番号は、label ではなく封印の記録（追記のみ）の長さで決まる。

## 5. 封印の時機と、取り直しをしないこと

- **手法を作る期間の区画は、正式な run（run_id 4199ae53d35b918a。seq 12 で封印したマニフェスト）の結果で確定とし、取り直さない**（T-087 の監査 中-1）。
  - 理由：欠けた日の件数と日付（`files_ok` による48日）は、T-082 の監査と T-087 で既に知られている。この後に取り直しを選べると、結果を見てから欠けた日を変えられる。
  - 支える仕組み：入口の `official_day_records()` は、封印の記録に official の gkg-run-start がちょうど1件のときだけ読み、2件目があると止まる。そのため、取り直しの正式な run を始めると、この一覧のコードは動かなくなる。
  - したがって、この区画では「封印より前に取り直したら一覧を作り直す」という道は使わない。candidates.md 3章 (5) の取り直しの手順は、ほかの区画（閾値を決める期間・基準値を測る期間・前向きの予言）に当てはまる。
- **判定（島かどうか）を一つも計算しないうちに封印する。**
- **順番5（タグの一覧の結果）より前に封印する。** candidates.md 3章 (5) は「モデルより前（遅くとも threshold-access より前）」とするが、順番5 より前に置けば、この両方より前になる。順番4 を順番5 より前に封印することの強制は、封印係のタスクで扱う（T-087 の監査 中-3）。
- 封印の kind、記録の中身、照合（出力の sha256、コードと文書の sha256、マニフェストの gkg-run-result の seq との対応）は封印係が決める（reviews/T-085.md のリードの判断 3）。

封印の対象として想定しているもの：
- 上のコマンドの出力（JSON）とその sha256
- この文書
- `src/stats/missing_days.py`（中で使う `src/stats/candidates.py`・`src/stats/periods.py`・`src/stats/counting.py` は封印済みの版と同じもの）
- `tests/stats/test_missing_days.py`

## 6. 順番5 との関係

- 順番5 の記録は、参照に**この順番4 の記録（seq と出力の sha256）**を入れる（reviews/T-085.md のリードの判断 2。4-2）。
- 順番5 では、欠けた日の比率を値なしとして扱う（candidates.md 冒頭の r(d) の定義：欠けた日は値を持たない）。どの日が欠けた日かは、この一覧だけで決め、順番5 の中で数え直さない（統計係の提案）。
- 参照を記録に入れる仕組みは封印係のタスクで扱う。

## 7. 限界

**2020年秋の欠け**：T-082 の監査は、`files_ok` の条件で欠けた日を48日と見込んだ。2015-05-29、2015-10-21、2015-10-22 と、2020-09-28〜11-17 のうち45日である。2020年秋の欠けは、手法を作る期間の区画の終わり（2020-12-14）に近い。

この欠けの影響について、T-085 の報告は次のように見込んだ。**どれも推測で、データで確かめてはいない。**
- （推測）2020年秋の欠けはエンバーゴの中にあり、期間の区切りは変わらない。
- （推測）手法を作る期間の最後の数回の予言で、判定期間が欠けた日に入る。判定期間の7日のまとまりに欠けた日があればそのまとまりは使わないので、判定不能の予言が増えうる。
- （推測）手法を作る期間の最後の四半期では、存在の条件で外れるテーマが増えうる。
- （推測）閾値を決める期間の最初の約1年の予言では、普段の水準 B(t)（t-371 から t-1）がこの区画の日を読む。欠けた日は使えるまとまりを減らすので、B(t) と、一度跳ねたタグの扱い（冷却）に響きうる。

ほかの限界：
- 欠けた日は日単位で決まり、タグに依らない。一部が欠けた日の比率は、取得できたファイルの時間帯に偏りうる（candidates.md 3章 (5) の72本の理由のとおり、大きさよりばらつきに効くと見込む。これもデータで確かめていない）。
- `files_ok` は収集係のコードが数えた値で、この一覧のコードは数え直さない。C7 の分母は、封印済みの counting.py が、sha256 を照らした日の集計から数える。どちらも、数え方の正しさは収集係・統計係（順番1b）のテストと、封印係の照合に依る。

## 8. 何を知っていた時点で決めたか

事実の順序は次のとおりである。
- 72本と欠けた日の規則は、seq 2（2026-10-06）で封印済みで、データを見る前に決めた。
- `files_ok` の条件で欠けた日が48日になることは、T-082 の監査で既に知られていた。T-087 の一覧はそれを確かめたもので、この件数を見てから規則や72本を決めたのではない。
- 全体の報道量の読み方（C7 の分母）は、reviews/T-087.md 3章で、日の集計を開く前に確定した。C7 の分母が0の日があるかどうかは、T-089 で日の集計を開くまで分からなかった。
- T-089 の結果（件数・日付・分母が0の日）を見て、規則・読み方・72本の値・入力の検査を変えない。
- テストは、本物のマニフェストでは day の行の検査だけを流し、件数や日付を固定しない。本物の日の集計はテストでは開かない。
